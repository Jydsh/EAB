# EAB 长期记忆分层设计（对照“聊到第 100 轮”视频）

> 日期：2026-11-24
> 视频：`https://v.douyin.com/eMhzFBLsQRo/`《做长期 Agent，怎么做到聊到第 100 轮》
> 结论：可以按行业常见的“工作记忆 / 语义画像 / 情景记忆 / 程序记忆”四层来设计。EAB 已经有四类记忆、混合召回和摘要，不需要推倒重来；真正要补的是**结构化事实、自动抽取、全量候选召回、遗忘与评测**。

## 1. 视频提出的记忆需求

视频的核心不是“把全部聊天塞进 prompt”，而是“怎么挑选、怎么压缩、怎么丢弃”。它建议三层：

| 层 | 作用 | 视频里的例子 |
| --- | --- | --- |
| 短期记忆 | 保持当前对话连贯 | 最近 N 轮原始对话，“刚看完电影”下一句“好不好看”能接上 |
| 实体画像 | 记住精确事实 | 第 1 轮“我叫小张，小时候被狗追过很怕狗”抽成结构化卡片，之后直接查表 |
| 长期情景 | 记住故事、感受、零散经历 | “之前聊过什么开心的事”按语义相似度召回片段 |

另外两个工程要求：

1. **异步形成记忆**：用户发消息后先正常回复，后台单独抽取实体、向量化、入库，不让用户等。
2. **动态维护**：新增、冲突校验、清理过期信息，记忆要持续迭代，不是存进去永远不动。

这套思路和 MemGPT / Letta、Mem0、LangMem、Zep 等长期记忆方案的分层方向一致：工作记忆、语义事实、情景片段、程序性偏好分别存储，再在每轮按预算拼装。

## 2. EAB 当前实现

### 2.1 已有的四类长期记忆

`packages/server/src/memory-os.ts` 和迁移 `0096_memory_os.sql` 已实现：

- `preference` 偏好：不衰减；
- `fact` 事实：不衰减；
- `decision` 决策/口径：不衰减；
- `episode` 情景：45 天指数衰减，最低保留约 45% 权重；
- 写入前做重复/冲突检测，冲突进入待确认，不静默覆盖；
- 召回是词面 + 向量混合分，向量模型不可用时退回词面；
- 个人记忆本人确认，部门/公司记忆需要管理员确认。

这比视频多了一层“程序记忆”（偏好/决策），治理也更严格。

### 2.2 当前对话上下文

`routes/chat.ts` 每轮装配：

- 最近 8 条原始消息（`historyOf` 默认 `limit=8`）；
- 会话滚动摘要，最多 1800 字（`chat-summary.ts`）；
- 长期记忆最多 3 条；
- 同会话旧消息 FTS5 召回最多 5 条、1800 字，且默认只在明确回顾、短追问或具体标识符时触发；
- 跨会话检索默认关闭，只有用户明确说“上次/之前/历史记录/那个对话”才开。

### 2.3 和视频逐项对照

| 视频要求 | EAB 现状 | 判断 |
| --- | --- | --- |
| 最近 N 轮原始对话 | 8 条原文 + 滚动摘要 | 基本有，窗口偏短，但有摘要补位 |
| 结构化实体画像 | `fact` 是自由文本，没有 subject / predicate / object 槽位 | **缺结构化** |
| 精确事实查表 | 事实也走词面/向量召回，最多取 3 条 | **会被 top-k 截断** |
| 情景片段向量库 | `episode` 有 embedding、余弦召回、45 天指数衰减 | 基本有，但没有聚类和事件结构 |
| 自动后台抽取 | 只有模型主动调用 `memory.propose` 才写入 | **没有自动形成记忆** |
| 动态更新/冲突/遗忘 | 有冲突待确认；情景只做排序衰减，事实没有有效期和清理 | **半套** |
| 第 100 轮记住第 1 轮 | 受“候选只取最近 20 条 + 最终只注入 3 条”限制 | **有明确风险** |

## 3. 最关键的问题

### 3.1 候选池只有最近 20 条

当前代码：

```sql
SELECT ... FROM memories
 WHERE ... confirmed = 1 ...
 ORDER BY created_at DESC LIMIT 20
```

然后在这 20 条里做混合召回，最终只注入 3 条。也就是说，即使第 1 轮的事实已经入库，只要后面新增的记忆超过 20 条，它可能连候选都进不了，更不可能被注入。

这是“聊到第 100 轮还记得第 1 轮”最直接的障碍，优先级高于换更大的模型。

### 3.2 `fact` 不是结构化事实

现在一条 `fact` 就是一段自由文本，比如“我叫小张，小时候被狗追过很怕狗”。它能被语义召回，但不能：

- 按 `subject=小张 / predicate=怕 / object=狗` 精确查询；
- 区分“当前有效”和“已过期”；
- 判断新事实是补充、修正还是冲突；
- 生成稳定的“用户画像卡”。

视频说的“查表调取事实不会丢不会错”，前提就是结构化，不是把整句话塞进向量库。

### 3.3 没有自动抽取

`memory.propose` 是模型工具，只有用户说“记住”或模型判断要记时才写。普通聊天里的“我叫小张”“我怕狗”不会自动形成记忆。视频要求的是每轮后台抽取，这是 EAB 和“长期 Agent”最大的行为差异。

### 3.4 冲突和遗忘不够

- 冲突判定是字符二元组 Jaccard，阈值 0.5，同义不同表述可能漏拦；
- 事实没有 `valid_from / valid_to`，旧事实不会因为新事实自动失效；
- 情景只有排序衰减，没有归档或删除；
- 已有 `DELETE /api/memories/:id` 软删除接口，但没有物理清理、向量清理和“失效/过期”语义，用户也看不到“为什么这条不该再被想起”。

## 4. 建议的标准设计：Memory OS v2

不推倒现有四类，直接在它们上面补“结构化 + 自动抽取 + 全量召回 + 维护”。

### 4.1 四层职责

| 层 | 存什么 | 注入方式 |
| --- | --- | --- |
| 工作记忆 | 最近 8–12 条原文、当前任务、计划、 pinned 事实 | 每轮固定注入，原文优先 |
| 语义画像 | 结构化事实槽位：姓名、偏好、恐惧、项目、环境、负责人 | 按实体/键精确查询，生成画像卡 |
| 情景记忆 | 故事、经历、踩坑、有效步骤，带时间和显著性 | 向量 + 词面召回，按相关性取 2–3 条 |
| 程序记忆 | 偏好、决策、团队口径 | 固定注入或按场景过滤，不衰减 |

### 4.2 数据模型

在现有 `memories` 上增加可空字段，避免新建一套并行表：

- `subject`：事实主体，如“小张”“项目 EAB”；
- `predicate`：关系，如“怕”“负责”“部署在”；
- `object_text`：值，如“狗”“网关”；
- `fact_key`：稳定键，如 `user.fear`、`project.owner`，用于精确覆盖；
- `confidence`：抽取置信度；
- `source_message_id`：证据消息，支持回溯；
- `valid_from / valid_to`：有效期；
- `last_access_at`：最近使用时间；
- `importance`：显著性，供排序和清理；
- `sensitivity`：普通/敏感，敏感事实不自动注入公司上下文。

`episode` 继续复用 `content + embedding`，另加 `event_at`、`salience`、`source_message_id` 即可；不需要马上做复杂事件图。

### 4.3 写入管线

每轮回复完成后异步执行，不阻塞用户：

1. 取本轮用户话 + 助手结论 + 当前画像卡；
2. 用小模型抽 JSON：`facts[] / episodes[] / preferences[]`，每条带 `subject/predicate/object/evidence`；
3. 确定性过滤：长度、PII、密钥、租户范围、重复；
4. 事实按 `(company, scope, fact_key)` 查旧值：
   - 相同：跳过；
   - 补充：新增；
   - 冲突：新值进待确认，标 `conflict_with`；
5. 情景写 `episode` 并 best-effort 生成向量；
6. 默认开启个人高置信自动生效；`EAB_MEMORY_AUTO_CONFIRM=off` 可退回影子模式。

自动确认策略（2026-11-24 已实现）：

- 个人范围：事实置信度 ≥ 0.85、偏好/决策 ≥ 0.8，且无冲突时直接生效，不需要用户再去设置里点确认；生效后仍可在“我的记忆”里查看、修改、删除；
- 冲突、低置信、情景候选仍留在待确认区，不静默覆盖；
- 部门/公司记忆：必须管理员确认，不自动扩散；
- 自动生效只覆盖用户本人上下文，不改变团队共享记忆的审核门槛。

### 4.4 召回管线

每轮按以下顺序，不再只从最近 20 条里挑：

1. 查询分析：抽实体、时间、意图；
2. 画像查询：按 `subject/fact_key` 精确取当前有效事实，生成 5–8 条“用户画像卡”；
3. 情景召回：全量候选向量 + 词面混合，取 2–3 条；
4. 历史补召回：同会话 FTS5；跨会话仍只在明确指代时开；
5. 统一打分：`相关性 0.6 + 新近度 0.2 + 重要性 0.2`，做 MMR 去重；
6. 预算裁剪：画像卡 800–1200 字，情景 600–900 字，总记忆注入不超过 2000 字；
7. 写 `memoryRecallTrace`：命中来源、分数、是否精确查表、是否被预算丢弃。

### 4.5 维护

- 事实冲突：精确键覆盖 + 语义相似辅助；新事实确认后旧事实写 `valid_to`，不物理删除；
- 过期：项目、环境、负责人这类事实可设有效期；过期事实不再注入，但保留审计；
- 情景衰减：保留现有 45 天半衰期，低于阈值归档，不直接删；
- 合并：夜间把同一主题的重复情景合并成一条摘要，保留来源；
- 忘记：用户可删除单条；删除后同时清向量和 FTS 索引；
- 评测：F 阶段已拆成 100 条抽取基准与 100 轮针事实选择探针，分别测误写/漏写和长轮次召回；token 开销与真实 100 轮对话端到端评测仍待补。

### 4.6 D 阶段落地参数（2026-11-24）

- 迁移 `0103_memory_maintenance.sql`：`memories` 增加 `archived_at / cluster_key / merged_from / recall_count / last_recalled_at`，新增 `memory_maintenance_runs` 运行记录表；
- 情景合并：同范围、最近 60 天、相邻不超过 7 天、相似度 ≥ 0.55，每组至少 2 条；合并记录写 `extraction_source='consolidated'`、`cluster_key='ep_<sha1前16位>'`、`merged_from` 为来源 id 数组，正文去重拼接且不超过 500 字，原始记录归档保留审计；
- 情景归档：超过 120 天且 `recall_count=0` 的已确认情景进入归档，不物理删除；召回候选统一过滤 `archived_at IS NULL`；
- 调度：20 小时内不重复运行；后台 worker 启动后延迟 60 秒首跑，之后每 6 小时检查一次；
- 召回门槛：词面命中，或向量相似度 ≥ 0.70；最多 4 条；按 `相关性 0.6 + 新近度 0.2 + 重要性 0.2` 排序；
- 召回解释：每条返回 `score / relevance / vectorScore / keywordHits / reasons`，命中后 `recall_count` 加一并写 `last_recalled_at`；解释随消息 meta 的 `longTermMemoryRecall` 持久化，刷新后仍可展开；
- 管理面板：状态页签 `active / pending / conflict / archived / expired / all`、统计条、关键词搜索、“立即整理”入口；个人记忆自动生效说明直接显示在面板顶部。

### 4.7 E 阶段落地参数（2026-11-24）

- 迁移 `0104_memory_extraction_runs.sql`：新增抽取运行记录表，只存渠道、模式、计数和耗时，不存用户原话；
- 入口：网页 `web`、钉钉 `dingtalk`、飞书 `feishu` 统一调用 `extractMemoryShadow`，回复后再异步抽取；
- 统计：`GET /api/memories/stats` 返回近 7 天抽取轮次、抽取/写入/生效/待确认/冲突/重复/敏感跳过、生效率/重复率/冲突率、渠道分布；
- 面板：“我的记忆”显示近 7 天抽取质量，用来观察自动生效是否写入过多、冲突是否异常；
- 边界：统计只按当前成员自己的运行记录计算；运行记录写入失败只写日志，不影响记忆本体。

### 4.8 F 阶段落地参数（2026-11-24）

- 迁移 `0105_memory_benchmark_runs.sql`：新增基准运行记录表，保存计数、通过率、漏写/误写/敏感泄漏、100 轮召回排名和失败用例编号，不保存合成用例原文；
- 抽取基准：固定 100 条合成用例，`60` 条应抽取、`30` 条应忽略、`10` 条敏感凭证；纯函数评估器只做分类判断，不写真实 `memories`；
- 指标：命中率、漏写率、误写率、敏感泄漏数、总通过率；应抽取用例按记忆类型命中，应忽略用例不得产生候选，敏感用例必须被 `memoryLooksSensitive` 拦住；
- 召回探针：1 条针事实 + 99 条项目噪声，第 100 轮用 `limit=4` 的选择策略验证针事实是否仍在窗口内，并记录排名；它验证的是存储与选择策略，不是实际跑 100 轮对话；
- 接口：`POST /api/memories/benchmark/run` 需要 `memory:write`，写审计 `memory.benchmark`；`GET /api/memories/stats` 返回 `benchmark.dataset` 与 `benchmark.lastRun`；
- 面板：显示最近一次通过率、漏写、误写、敏感泄漏和 100 轮召回排名，并提供“运行评测”入口；
- 真实基线（2026-11-24）：100 条通过 92 条（92%），命中 56、漏写 4（6.7%）、误写 4（13.3%）、敏感泄漏 0，100 轮针事实召回排名第 1；
- 已知边界：规则抽取对比较级恐惧、否定偏好、“更习惯”句式和第三方转述中的第一人称片段仍有漏写/误写；LLM 抽取和真实 100 轮对话端到端评测尚未纳入本轮。

## 5. 分阶段落地

| 阶段 | 内容 | 预估 |
| --- | --- | --- |
| A | 去掉“最近 20 条”候选上限，改为按范围 + 类型 + 向量/FTS 全量候选；补 100 轮针事实测试 | 1–2 工程日 |
| B | `memories` 加结构化事实字段，生成画像卡，精确键查询；迁移历史自由文本事实 | 3–5 工程日 |
| C | 异步抽取，个人高置信自动生效（默认开启，`EAB_MEMORY_AUTO_CONFIRM=off` 可退回影子模式）；补冲突/过期/删除链路 | 3–5 工程日 |
| D | 情景聚类、夜间合并、记忆管理 UI 增强、召回解释（2026-11-24 已实现） | 3–5 工程日 |
| E | 网页/钉钉/飞书全入口统一抽取，运行记录与近 7 天质量统计（2026-11-24 已实现） | 1–2 工程日 |
| F | 100 条抽取基准、100 轮针事实召回探针、“我的记忆”运行入口与最近结果（2026-11-24 已实现） | 1–2 工程日 |

A–B 已经改善了“第 100 轮记不住第 1 轮”；C 的关键是个人高置信自动生效，团队/公司仍保留管理员确认，避免个人判断污染共享上下文，E 再把这套规则统一到三个入口，F 提供可重复的质量基线。

## 6. 验收口径

1. 100 轮测试里，第 1 轮明确的 10 条针事实，第 100 轮问到时应召回 ≥ 9 条，且不混入其他用户/公司的记忆；F 当前先用 1 条针事实验证选择链路，10 条针事实与真实模型对话版仍待补。
2. 画像卡中的事实必须带来源消息和确认状态；用户能在“我的记忆”里改、删、失效。
3. 冲突不得静默覆盖；新事实确认后旧事实进入失效状态。
4. 没有向量模型时，结构化事实仍能精确召回；情景退回词面召回，不阻断回答。
5. 记忆注入 token 不超过总上下文的 15%，P95 召回额外耗时不超过 50ms。
6. 个人高置信事实/偏好自动生效且随时可删；冲突与低置信仍进待确认；关闭 `EAB_MEMORY_AUTO_CONFIRM` 可退回影子模式量化误写率。

## 7. 结论

可以按视频里的三层思路设计，但不要照抄成“短期 + 事实 + 向量”三张表就结束。EAB 已经是“四类记忆 + 混合召回 + 摘要”的结构，缺的是：

1. 结构化事实画像；
2. 全量候选召回，而不是最近 20 条；
3. 后台自动抽取；
4. 有效期、遗忘和可重复的评测基线。

A–F 已把前三项和“可重复评测”落地：F 阶段现在能固定跑 100 条抽取基准和 100 轮选择策略探针，并留下计数与失败编号。下一步不应继续堆规则，而是补齐真实 100 轮对话端到端评测、LLM 抽取对照和 token/P95 观测，再决定是否把自动记忆扩大到团队范围。
