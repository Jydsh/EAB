# EAB P1 · 团队复杂度门禁（AGT-11）

> 日期：2026-11-24
> 对应审计项：`docs/EAB-Agent框架对照审计与能力建设需求-2026-11-23.md` 的 AGT-11
> 目标：单步问答 / 单文件任务不强制编队；只有确实可拆、可独立验收的任务才派 2–4 个子 Agent，并把编队理由落库可回看。

## 一、升级前的缺口

- 前台编队只靠 `looksLikeBackgroundDispatchTask` 判：只要命中“实现、开发、修复、调研、分析”等强动作词就强制第一次调用 `agent_spawn`。
- 单步问答虽然拦了“如何/怎么”开头，但“怎么做登录鉴权并实现”这类带执行词的问句仍会被误判；`修复这个文件`、`改这份周报`也会被强行动队。
- 强制编队提示写死了“能拆就派 2–4 个”，但没有告诉模型判定依据，也没有记录“为什么这一轮要编队”。
- 运行详情只有父子树和工具轨迹，无法回答“这轮到底该不该编队、最后真派了几个”。

## 二、确定性分诊

新增纯函数 `decideTeamFormation()`，位于 `packages/server/src/agent-team-formation.ts`。它只读用户本轮原话和当前文件上下文，不调用模型，判定顺序固定：

| 优先级 | 命中条件 | 结果 |
| --- | --- | --- |
| 1 | 子 Agent 完成/失败/提问通知 | 不编队，避免唤醒轮递归派活 |
| 2 | 用户明确点名“3 个员工 / 团队分工 / 并行 Agent” | 强制编队，目标 2–4 个 |
| 3 | 问句且没有执行动作（如何实现、解释一下、是什么） | 不编队 |
| 4 | 单文件/单文档局部处理，且没有“整个项目/所有文件/批量” | 不编队 |
| 5 | 单点修复/小改（bug、错别字、格式、按钮、一行） | 不编队 |
| 6 | 命中至少一个真实多切片信号 | 强制编队，目标 2–4 个 |
| 7 | 请求过短或没有多切片信号 | 交回主 Agent 自行判断，不硬拆 |

多切片信号只收“能独立验收”的结构性证据，不把顺序动作当成可并行任务：

- 端到端交付：`完整项目/完整系统/整个项目/从零搭建/全流程`；
- 多个模块、页面、接口、方向、报告、角色；
- 前后端/数据库并行交付；
- 用户明确要求分别、各自、并行、分头；
- 多文件/批量处理；
- 两个以上不同交付物；
- 编号需求清单。

“分析数据并写报告”“修复后跑测试”这类顺序依赖不会被单独的“并/然后”触发强制编队，避免派出互相等待的岗位。

## 三、运行时接入

`packages/server/src/routes/chat.ts` 的 `forceTeamFormation` 改为：

```text
文本判定 force
  && depth = 0
  && allowAgentWait = false
  && 无用户附件
  && 非出题模式
  && 本轮有 agent_spawn
  && 没有正在跑的子任务
```

任一环境条件不满足时，保留文本判定但记录拦截原因，不注入强制编队提示。

强制编队时：

- `dispatchToolChoice` 仍把本轮第一次工具调用锁到 `agent_spawn`，且提示里带上具体判定依据；
- 提示明确“应派 2–4 个互不依赖、可独立验收的切片”；
- 同时允许把“实现后立刻跑测试”这类强依赖步骤合并到同一岗位，避免为了凑人数拆出等待链；
- 原有 `agentMaxParallel` 上限（默认 4）继续兜底，超过直接 422，不静默丢任务。

## 四、编队理由落库

新增迁移 `packages/storage/migrations/0095_agent_run_formation.sql`：

```sql
ALTER TABLE agent_runs ADD COLUMN formation_json TEXT;
```

根 run 在模型第一次调用前写入 `formation_json`，字段包括：

- `force`：文本判定是否可编队；
- `reason`：`complex_multi_slice` / `explicit_team_request` / `single_step_question` / `single_file_operation` / `single_point_change` / `short_or_chat` / `ambiguous_model_choice` / `internal_message`；
- `detail`：中文判定理由，同时注入强制编队提示；
- `signals`：命中的确定性信号，便于排查误判；
- `applied`：文本判定后是否真的触发了强制编队；
- `blockedBy`：被哪些运行时条件拦截（附件、出题、已有子任务等）；
- `decidedAt`：判定时间；
- `spawnedAgents`：实际成功建出的子任务数，派发后补记，不覆盖原因。

历史 run 没有记录时 `formation=null`，不伪造理由。

## 五、控制台展示

`/api/console/agent-runs/:id` 返回的每个 run 新增 `formation`。任务详情弹层在失败原因下方展示：

- “编队门禁 · 已强制编队 / 未强制编队 / 判定可编队但被运行时条件拦截”；
- 中文理由、命中信号标签；
- 实际派出人数和拦截条件（有值时）。

## 七、边界

- 门禁只决定“是否强制编队”，不替代模型对任务内容的最终拆分；模型仍可把实际强依赖步骤合并，避免制造等待。
- 2–4 是编队目标与提示约束，不是数据库硬约束；实际派发人数由 `spawnedAgents` 记录，超过 4 仍由既有并行上限拒绝。
- 分类器是确定性规则，新增业务话术可能带来误判；后续应优先补判定测试，而不是继续往正则里堆关键词。
