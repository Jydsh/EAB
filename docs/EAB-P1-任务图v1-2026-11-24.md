# EAB P1 · AGT-16 任务图 v1 交付说明

日期：2026-11-24  
范围：AGT-16 任务图 v1（线性、条件分支、工具、子 Agent、人工、等待）  
当前版本：`2026.11.23.04`（本轮未变更版本号，未 commit，未 push）

## 1. 交付结论

AGT-16 v1 已落地，按审计要求先做到“能定义、能跑、能查”：

- **能定义**：控制台任务中心提供节点卡片表单编排，按节点类型填写工具、子 Agent、人工、等待、条件分支字段；顶部有只读自动布局流程图和四类起步模板；工具、模型、角色、条件字段提供候选 ID 自动补全；高级 JSON 保留为兜底。
- **能跑**：运行只读已发布版本；支持线性链路、条件分支、工具节点、子 Agent 节点、人工节点、等待节点。
- **能查**：每次运行生成唯一 `traceId`，步骤 append-only；可按 `traceId` 或 `runId` 查完整执行记录。
- **可版本化**：草稿与发布版本分离；保存新草稿不影响已发布版本运行；再次发布才切换新版本。
- **人工 / 等待可恢复**：人工节点持久暂停，通过 / 拒绝后继续；等待节点到点由后台 worker 自动恢复。
- **v1.1 执行加固**：补上重复 id、拒绝边成环两类校验漏洞；运行租约 + 心跳 + 崩溃恢复；可中止取消；数据库级并发 `claim`；启动改为后台执行、前端轮询；人工节点按 `assigneeRole` 鉴权。
- **v1 不做**：拖拽画布、自由连线、缩放 / 小地图、并行分支、循环、节点级自动重试、超时自动失败。v1 的可视化是“只读自动布局流程预览 + 下方节点表单”，拖拽画布留到 P2。

## 2. 为什么新建独立任务图，而不是直接复用审批流

现有 `approval-workflows.ts` 有可复用的版本化骨架，但它的语义只服务“权限申请审批”：

- 节点类型只有 `start / condition / approval / cc / end`；
- 执行动作固定为审批人流转；
- 无法表达工具调用、子 Agent、等待恢复。

为避免审批语义污染通用编排，AGT-16 新建 `task-graph.ts` 与独立表；只复用已有的控制台身份、工具执行入口、Agent 回合入口和审计写入。

## 3. 数据模型

迁移：`packages/storage/migrations/0097_task_graphs.sql` 建四张主表；`0100_task_graph_leases.sql` 为运行表补租约与取消字段。

| 表 | 作用 |
| --- | --- |
| `task_graphs` | 任务图主表：名称、说明、状态、当前发布版本、草稿版本 |
| `task_graph_versions` | 版本表：`draft / published / superseded`，发布版本冻结 `definition_json` |
| `task_graph_runs` | 运行表：`trace_id`、发布版本、发起人、状态、输入、变量、当前节点、等待信息；v1.1 增加 `lease_owner / lease_until / cancel_requested_at` |
| `task_graph_steps` | 步骤表：按 `seq` append-only，记录节点输入、输出、错误、耗时 |

运行租约默认 60 秒，执行期间每 10 秒续租；`cancel_requested_at` 记录取消请求，跨进程由心跳和节点边界检查生效。

一次运行对应一个 `traceId`（`trace_<hex>`），`runId` 形如 `tgr_<hex>`，步骤 `stepId` 形如 `tgs_<hex>`。

## 4. 节点语义

定义结构：

```json
{
  "entry": "start",
  "nodes": [
    { "id": "start", "kind": "start", "title": "开始", "nextIds": ["lookup"] }
  ]
}
```

支持节点：

| kind | 作用 | 必填 |
| --- | --- | --- |
| `start` | 唯一入口，一条出线 | `nextIds` |
| `tool` | 调已有工具，参数支持 `{{input.question}}` 模板 | `tool`；`args` 可选 |
| `agent` | 起一个子 Agent 回合 | `agent.modelId`、`agent.prompt`；`maxRounds` 可选 |
| `manual` | 人工暂停，等待通过 / 拒绝 | `nextIds`；`manual.instructions` 可选 |
| `wait` | 等待 `durationSec` 秒后自动恢复 | `wait.durationSec`，默认 60 |
| `condition` | 按变量判断走哪条出线 | 至少两条 `nextIds`，每条要有 `edgeRules` |
| `end` | 结束，不能有出线 | 无 |

条件规则支持：

- 字段路径：`input.question`、`nodes.lookup.count`、`nodes.lookup.hits.0.title`；
- 操作：`eq / neq / contains / gt / gte / lt / lte / exists / empty / truthy`；
- 每个条件节点最多一个 `{ "else": true }` 兜底分支。

人工拒绝：

- 默认直接结束为 `rejected`；
- 配了 `manual.rejectNextId` 时，拒绝后转到指定节点继续执行。

## 5. 校验规则

发布前必须通过 `validateTaskGraph`：

- 必须且只有一个 `start`，入口必须是 `start`；
- 至少一个 `end`，所有节点从入口可达；
- 不能有循环；可达性、环检测和执行边都包含 `manual.rejectNextId`，拒绝边不能回到 `start`；
- 节点 id 唯一，重复 id 直接报错，不再被内部映射静默覆盖；出线目标必须存在，不能自连、不能重复；
- `manual.rejectNextId` 不能为空字符串、不能指向自身、不能指向不存在的节点；
- 非条件节点最多一条出线；
- 条件节点每条出线必须有规则，最多一个 `else`；
- 工具节点必须有 `tool`；子 Agent 节点必须有模型和指令；
- 子 Agent `maxRounds` 限制 1–20；等待 `durationSec` 限制 1 秒到 30 天；
- 最多 100 个节点；单次推进会做 200 步保护。

## 6. 执行与恢复

核心入口：`packages/server/src/task-graph.ts`

- `createTaskGraphRun` / `runTaskGraphRun`：创建运行与后台推进分离；启动和人工通过都先落库再返回，后台继续执行；`startTaskGraphRun` 保留原语义，供测试和内部调用同步等待结果；
- `decideTaskGraphManual`：只允许 `waiting_manual` 状态，先用数据库原子 `claim` 抢占运行再推进；通过后继续，拒绝后结束或走 `rejectNextId`；节点 `manual.assigneeRole` 非空时，处理人角色必须匹配该角色或包含 `super_admin`；`deferAdvance` 为真时只落库并返回 `running`，由调用方自行启动后台执行；
- `resumeDueTaskGraphRuns`：扫描到点的 `waiting_wait` 运行，同样先 `claim` 再推进；
- `claimRun`：用 `UPDATE ... WHERE status = 期望状态` 做数据库级抢占，多实例同时扫描时只有一个能推进；
- `heartbeatRun` / `assertRunActive` / `startRunHeartbeat`：执行期间每 10 秒续租；心跳发现租约丢失或已请求取消时中止本地控制器；工具 / Agent 返回后、每个节点边界都会检查运行是否仍由自己持有；
- `recoverStaleTaskGraphRuns`：扫描租约过期，或旧运行长时间未更新的 `running` 记录，标记 `failed`（已有取消标记则标 `cancelled`），并同步收尾未完成步骤；不自动重试节点，避免重复副作用；
- `cancelTaskGraphRun`：写取消标记并中止同进程活跃控制器，把所有 `running / waiting` 步骤改为 `cancelled`；跨进程取消由心跳和节点边界检测；
- `getTaskGraphRunByTrace`：按 `traceId` 查运行和全部步骤，并带上运行对应的发布定义，便于运行态回放；
- 同一 run 的推进同时有进程内串行锁和数据库租约，人工通过、等待 worker、多实例扫描不会重复推进。

执行器由控制台注入：

- 工具节点走 `executeTool(deps, actor, tool, args, {kind:'cloud'}, { traceId, turnId, idempotencyKey, signal })`；
- 子 Agent 节点走 `runAgentTurn({...})`，返回文本与子 runId，并把 `signal` 透传下去；
- `traceId` 同时作为工具上下文 trace 和 Agent 回合 turnId；
- 工具幂等键为 `task-graph:<traceId>:<nodeId>`，重复推进不会重复产生写入型副作用。

**身份边界**：运行和人工处理使用当前控制台会话解析出的真实 actor；成员后台会话不会被无条件提升为 `super_admin`。等待节点自动恢复时，按 run 的 `userId` 重新组装发起人身份；发起人是控制台操作员时使用控制台身份，普通成员已停用或不存在则停止自动恢复并报错，不再用超管兜底。

## 8. 控制台界面

入口：控制台 → 运营与审计 → 任务中心 → 顶部「任务图」标签。任务图已从“定时任务”列表底部拆成独立标签，不再和定时任务表混排。

**任务图与定时任务的区别**：定时任务解决“什么时候触发一条指令”，例如每天 9 点提醒、定时推送；任务图解决“这条指令要经过哪些步骤”，例如先查知识库、再按问题类型分流、金额超限转人工审批、最后汇总输出。任务图本身不负责定时触发，后续可以把“定时触发”作为运行任务图的一种入口。

### 8.1 节点卡片表单编排

右侧不再默认显示一大块定义 JSON，而是按节点渲染卡片：

- 左侧任务图列表，显示状态、版本、草稿版本；
- 右侧名称 / 说明 / 状态，下面依次是三步引导、起步模板、流程图预览、节点卡片；
- 新建时显示三步引导：选模板或插入节点 → 在卡片填工具 / 模型 / 规则 → 校验后保存；
- 节点类型不再用下拉框，改为五个一键按钮：“+ 工具 / + 子 Agent / + 人工 / + 等待 / + 条件分支”；
- 节点默认插在当前选中节点之后；选中条件节点时，新节点作为该条件节点的一条新出线；
- 未选中节点时，新节点插在结束节点之前；
- 点击节点卡片、卡片内任意输入框或流程图节点，都会选中该节点并更新插入位置提示；点流程图节点还会滚动到对应表单卡片；
- 每个节点卡片可删除；开始和结束节点不可删除；删除普通节点时，出线尽量接到它的下一个节点；删除条件分支目标时，出线收敛到兜底目标，避免同一条出线重复。

流程图预览是只读自动布局：

- 从 `entry` 起按出线做最长路径分层，同层按发现顺序排列；
- 节点固定宽 176、高 78，水平间距 34、垂直间距 62，容器内滚动；
- HTML 绝对定位节点卡片，SVG 画贝塞尔连接线和箭头；
- 条件分支边显示规则摘要，例如 `input.question 包含 退款`、`否则`；
- `manual.rejectNextId` 画成红色虚线“拒绝”边；
- 图例区分正常流转、条件分支、拒绝后跳转；
- 节点标题、工具 ID、模型 ID、等待时长等字段修改后实时刷新流程图；结构或选中节点变化时同时刷新条件字段候选。

各节点表单字段：

| kind | 表单字段 |
| --- | --- |
| `start` | 下一步 |
| `tool` | 工具 ID、参数 JSON、下一步 |
| `agent` | 模型 ID、最大轮次、子 Agent 指令、下一步 |
| `manual` | 处理说明、处理角色、超时小时、拒绝后转到、下一步 |
| `wait` | 等待时长、单位（秒 / 分钟 / 小时 / 天）、下一步 |
| `condition` | 每条出线：走到哪个节点、是否“否则”、字段、操作符、值；可添加 / 删除出线 |
| `end` | 无字段，不能有出线 |

### 8.2 新手模板与 ID 自动补全

新建任务图提供四个起步模板，点击后替换当前节点，名称和说明若是模板自动生成值会一起更新，用户自定义过的名称和说明保留：

| 模板 | 结构 | 适用场景 |
| --- | --- | --- |
| 知识库问答 | 开始 → 检索工具 → 结束 | 制度、政策、FAQ 查询 |
| 条件分流 | 开始 → 条件分支 → 两条处理路径 → 结束 | 按输入内容走不同处理 |
| 人工审批 | 开始 → 人工确认 → 结束 | 工具或模型执行前暂停审批 |
| 定时等待 | 开始 → 等待 60 秒 → 结束 | 延时后继续 |

ID 自动补全来自控制台现有配置，不额外维护静态清单：

- 工具 ID：`GET /api/console/tools/access`，过滤 `available !== false`；
- 模型 ID：`GET /api/console/models`，过滤已启用且 `endpointKind` 为 `chat` 或 `systemone`；
- 角色代码：`GET /api/console/roles`；
- 条件字段：内置 `input.question / userId / date`，并按前序节点生成 `nodes.<id>`、`.text`、`.count`、`.result`、`.hits.0.title` 等候选。

界面使用原生 `datalist` 绑定：`#tg-tool-options`、`#tg-model-options`、`#tg-role-options`、`#tg-field-options`；候选加载失败不阻断手动填写，编排区显示“候选：N 个工具 · N 个模型 · N 个角色”。候选缓存 5 分钟。

### 8.3 高级 JSON 兜底

- 定义 JSON 折叠在“高级 JSON”里，默认不展示；
- 表单修改会实时同步到 JSON 预览；
- 直接修改 JSON 后必须点“应用 JSON 到表单”才生效；
- JSON 有语法错误、顶层不是对象、`nodes` 不是数组、节点缺 `id / kind` 时，保留原表单并在校验区显示错误，不再用 `alert`；
- 高级 JSON 修改后未应用时，校验 / 保存 / 发布会被拦截，提示先应用；
- 工具节点参数 JSON 非法时，校验 / 保存会在校验区指出具体节点和解析错误。

### 8.4 运行与运行记录

- 运行输入 JSON，按钮“运行已发布版本”；
- 点击运行后前端每 2 秒轮询运行详情，直到 `succeeded / failed / rejected / cancelled` 终态；
- 运行记录表：`traceId`、状态、开始时间、当前节点、通过 / 拒绝 / 取消；
- 点击 trace 打开步骤时间线，展示节点 kind、输入、输出、错误、耗时和当前等待信息。

### 8.5 表单状态与离开保护

- 名称、说明、任意节点字段修改都会标脏；
- 切换任务图或新建任务图前，如果有未保存修改，先弹确认；
- 运行已发布版本前，如果有未保存修改，提示“本次运行不会使用这些修改”；
- 保存成功后重新加载图详情，草稿版本和状态回到服务端真实值。

## 10. 已知边界

- 无拖拽画布、自由连线、缩放 / 小地图；v1 是只读自动布局流程预览 + 节点卡片表单，高级 JSON 只作兜底。
- 不支持并行分支（一个节点多条同时执行的出线）。
- 不支持循环；有环定义会被校验拒绝。
- 不支持节点级自动重试、超时自动失败、任务预算硬停；人工节点 `timeoutHours` 仍只作为展示信息，尚未执行超时策略。
- 人工节点 `assigneeRole` 已做处理人角色鉴权，但没有派单、转交和按角色通知。
- 取消是协作式的：工具 / Agent 必须响应 `AbortSignal` 才会尽快退出；不响应信号的长调用只能等租约过期或返回后由节点边界拦截。
- 变量持久化会压缩超长字符串、数组和深嵌套对象，避免单次运行把库撑大；被压缩后的超长字段不适合再做条件判断。
- 等待恢复 worker 每 5 秒扫描一次默认公司；多公司切换场景需要按公司分别启动 worker。
