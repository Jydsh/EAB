# 对话同步：只做钉钉 → 网页

## 口径

- **钉钉私聊 → 网页工作台**：钉钉机器人收到消息后，用户消息和机器人回复都会落库，
  并通过 SSE（`GET /api/chat/events`）实时推送到网页当前会话；左侧会话列表同步刷新。
- **网页 → 钉钉私聊**：不发送、不回写、不刷新钉钉卡片，也不进入钉钉侧模型上下文。
  网页对话只留在网页。

## 同一会话的消息顺序

- **默认排队**：上一轮还在流式输出时，新消息不打断上一轮，而是排到它后面。
  服务端 `acquireTurn()` 在同一 `sessionId` 上按 token 串行，网页端和钉钉入口共用这套顺序。
- **网页输入区**：流式回复期间仍可输入并发送；消息立即出现在对话里，但 AI 回复要等前一轮结束。
  输入区上方显示「正在回复，你的消息已排队（前面还有 N 条）」，并提供「停止当前回复并发送」。
- **停止语义**：点停止会断开当前 SSE，服务端通过 `AbortSignal` 中止在途模型流，释放会话锁，
  然后自动发送排队中的下一条。已经落库的历史不受影响。
- **切换会话**：未发送的排队消息会被取消，避免把旧会话的问题发到新会话。

## 来源标记

每条 `chat_messages.meta_json` 带 `channel`：

- 钉钉侧写入：`channel: "dingtalk"`，并带 `externalUserId`。
- 网页侧写入：`channel: "web"`，并保留附件等网页字段。

钉钉机器人构建上下文时调用：

```ts
historyOf(db, sessionId, 16, 'dingtalk')
```

只取 `channel = "dingtalk"` 的消息，因此网页里补问的内容不会被当成钉钉对话继续回答。
网页侧仍读取完整会话（含钉钉消息），以便在网页里连续查看同一条对话。

## 界面标记

- 钉钉来源消息：用户气泡旁、AI 回复底部显示「钉钉」小标签。
- 网页来源消息：显示「网页」小标签。

会话本身仍共用同一条（这样钉钉消息能在网页连续查看），但来源按消息区分，
不再按整条会话的 `chat_sessions.source` 判断。

## 验证

- 网页发「测试」→ 落库 `channel: "web"`，回复也是 `web`，没有触发钉钉卡片。
- 钉钉发「我想知道我的信息」→ 落库 `channel: "dingtalk"`，网页实时出现并带「钉钉」标签。
- `historyOf(..., 'dingtalk')` 单测：网页消息不会进入钉钉历史。
