# EAB AGT-21 压测与 SLO 基线 v1

日期：2026-11-25
范围：单实例、隔离种子库、mock 模型上游的全量可复跑基线；覆盖读接口、知识库读、50 并发对话、50 并发工具调用。
结论：**本轮基线 SLO 全部通过，判定为「部分落地（基线 v1）」**。真实厂商延迟、10 万 chunk 向量检索、子 Agent 并发和双实例仍未覆盖，不能把这份结果当成生产容量上限。

## 1. 为什么做这一轮

AGT-21 的原始验收是「首字时延、失败率、并发上限有基线；不靠感觉」。此前只有功能回归和单条手工会话，没有并发、延迟、错误率数据，也没有可重复执行的入口。

这一轮先解决三个问题：

1. 压测必须可复跑，不依赖某台机器上手工造的账号、模型和会话。
2. 压测不能碰正在使用的 `.eab-dev/eab.db`、8787/8788 服务和真实插件目录。
3. SLO 不能只看「平均耗时」，必须看 P95/P99、错误率、排队峰值和 SQLite 锁冲突。

## 2. 工具与隔离方式

新增 `scripts/perf.mjs`，入口：

```powershell
pnpm perf
pnpm perf:enforce
node scripts/perf.mjs --api=14 --chat=8 --tools=8
```

参数：

| 参数 | 默认 | 说明 |
|---|---:|---|
| `--api` | 200 | 只读 HTTP 请求总数 |
| `--api-concurrency` | 20 | 只读请求并发 |
| `--chat` | 50 | 对话消息条数，使用 50 个不同账号 |
| `--tools` | 50 | 工具调用条数 |
| `--enforce` | 关闭 | SLO 不通过时返回非零；默认只报告 |

隔离设计：

- `EAB_HOME`、`EAB_DB` 都指向 `.eab-dev/perf`，不读写真实 `.eab-dev/eab.db`。
- 先启动一次性种子实例，跑迁移、演示数据和管理员凭据；停掉后补 50 个压测账号 `u_perf_01` … `u_perf_50`。
- 再启动压测实例，服务端口、管理端口、mock 端口全部动态分配，不占用 8787/8788。
- mock 上游是 OpenAI 兼容 SSE 服务：`perf_chat`，首包固定 60ms，之后 9 个 token 每 45ms 一包，保证延迟可复现。
- 结果写入 `.eab-dev/perf/result.json`；`seed.log`、`server.log` 同目录保留，便于失败复现。

默认限额在脚本里显式固定，避免本机环境变量污染基线：全局对话 8、队列 100、单用户 0、每分钟 20、单模型 4、单公司 8；工具 8 / 200。50 条对话并发时，单模型 4 会主动形成排队，这正是本轮要验证的行为。

## 4. 场景与结果

### 4.1 只读 HTTP

200 个请求、20 并发，覆盖 8 类接口，每类 25 次：

- `GET /api/health`
- `GET /api/org/tree`
- `GET /api/org/members`
- `GET /api/kb/collections`
- `GET /api/kb/docs?collectionId=kb_all`
- `GET /api/kb/docs?collectionId=kb_mgmt`
- `GET /api/chat/models`
- `GET /api/tools`

组织树/成员接口需要 `org:dept:read` / `org:member:read`，`member` 角色没有这两个 scope，因此只读容量统一用 `company_admin`（`u_wf`）跑。成员访问组织接口返回 403 是权限设计，不计入服务端错误。

| 指标 | 实测 | SLO | 判定 |
|---|---:|---:|---|
| 成功 | 200 / 200 | 错误率 0% | PASS |
| P50 | 22.5ms | — | — |
| P95 | 30.6ms | < 250ms | PASS |
| P99 | 33.1ms | — | — |
| 最大 | 38.2ms | — | — |
| 吞吐 | 822.6 req/s | — | — |

分接口 P95 在 28.8–30.8ms 之间，没有单接口明显拖尾；知识库列表与文档读已包含在内。

### 4.2 50 并发对话

50 个账号各发 1 条 SSE 流式消息，消息只要求回复 `OK`。50 条全部成功：

| 指标 | 实测 | SLO | 判定 |
|---|---:|---:|---|
| 成功 | 50 / 50 | 错误率 0% | PASS |
| 首字 P50 | 3.55s | — | — |
| 首字 P95 | 6.20s | < 12s | PASS |
| 首字 P99 | 6.69s | — | — |
| 整轮 P50 | 3.92s | — | — |
| 整轮 P95 | 6.58s | — | — |
| 整轮 P99 | 7.05s | — | — |
| 吞吐 | 7.1 turn/s | — | — |

首字 P95 的 6.20s 主要不是模型慢，而是排队：单模型 4 并发，50 条约 7.1s 跑完，平均 7.1 turn/s。队列峰值 46 等于「50 条请求、4 条活跃」的直接结果，没有溢出或超时。

### 4.3 50 并发工具调用

50 并发调用 `math.eval`，全部成功：

| 指标 | 实测 | SLO | 判定 |
|---|---:|---:|---|
| 成功 | 50 / 50 | 错误率 0% | PASS |
| P50 | 55.3ms | — | — |
| P95 | 284.7ms | < 1s | PASS |
| P99 | 287.6ms | — | — |
| 最大 | 288.7ms | — | — |
| 吞吐 | 171.8 次/s | — | — |

`math.eval` 是本地只读工具，工具执行走 `acquireCoordinationSlot`，默认每工具 8 个名额；50 并发分波执行，P95 284.7ms 与这个并发上限吻合，说明没有失败、也没有把事件循环拖死。

需要注意：`/metrics` 的 `eab_tool_queued` 仍读旧的 `toolSemaphore`，与实际执行路径不是同一个对象，本轮结果里该值恒为 0，**不作为工具排队的证据，也不进入 SLO**。真实排队从耗时曲线判断；对外部 MCP / HTTP 工具的延迟仍不覆盖。

## 6. 未覆盖项（不要按「全量」对外说明）

1. **真实模型延迟**：mock 上游只有固定 60ms 首包和 45ms/包，真实厂商的网络、限流、推理耗时没有进入这份数字。真实首字约等于「本基线排队 + 厂商耗时」。
2. **10 万 chunk 向量检索**：知识库场景只覆盖列表和文档读接口，没有构造 NFR-P-04 要求的数据规模，也没有压 hybrid 检索、rerank 和向量库。
3. **子 Agent / 长上下文**：没有并发跑子 Agent、计划对象和多轮长对话，50 并发对话是短消息。
4. **双实例 / 多副本**：AGT-17 的容器化多实例没有在本轮验证，队列、迁移租约和跨实例协调仍是空白。
5. **并发上限**：50 是选定基线，不是实测最大承载。要回答「能撑多少人」，需要在目标部署机型上做阶梯加压，并记录拐点。
6. **外部工具**：`math.eval` 是本地工具，不代表 MCP、HTTP、A2A 工具的慢调用和超时行为。

## 7. 复跑与失败处理

```powershell
cd D:\AI kaifa\EAB
pnpm perf                 # 只报告
pnpm perf:enforce         # SLO 不达标时非零退出
```

如果失败：

1. 先看 `.eab-dev/perf/result.json` 的 `scenarios.*.failures` 和 `byCase`，确认是权限 403、模型不可见还是真实 5xx。
2. 再看 `.eab-dev/perf/server.log`，确认服务是否启动完成、端口是否被占用。
3. 如果是模型目录为空，检查 `perf_chat.roles` 是否包含 `member`；`roles` 为空字符串会被可见性逻辑判为不可见。
4. 如果打开临时库报 `disk I/O error`，先确认没有残留 node 进程；脚本已对服务退出后的 WAL 映射做重试。

压测库是一次性数据，每次运行都会重建；不要把它当业务库，也不要把 `u_perf_*` 账号写回真实库。

## 8. 状态判定

AGT-21 从「未开始」改为 **部分落地（基线 v1）**，理由：

- 已有可复跑脚本、隔离环境、固定 SLO 门槛和 `--enforce` 门禁。
- 读接口、知识库读、50 并发对话、50 并发工具四类场景已有 P50/P95/P99、错误率、对话队列和内存基线。
- 仍缺真实厂商、10 万 chunk、子 Agent、双实例和阶梯加压，不能算「全量压测完成」。

下一步如果继续 AGT-21，优先补：真实模型供应商的一组对照、10 万 chunk 检索、双实例下的队列与迁移租约，以及修正 `/metrics` 的工具排队指标（当前仍是旧 `toolSemaphore`，没有反映 `acquireCoordinationSlot` 的真实队列）。四项都应在目标部署机型上跑，而不是只在开发机。
