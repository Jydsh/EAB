# EAB v2026.11.23.03 发布说明

发布日期：2026-11-23
版本类型：补丁版本（数据类回答的合计与统计准确性）
发布基线：`main`

## 版本概述

`v2026.11.23.03` 是 `v2026.11.23.02` 的补丁版本，只处理“模型把业务数据算错”这一类问题：工具里的计算能力本身没问题，但模型拿到十几条带时长/金额的记录后会自己心算，漏行或算错合计。

## 问题与根因

- 现象：员工问本月加班总时长，模型调用业务接口拿到 17 条记录，逐条列得都对，合计却写成 188.55 小时。
- 实际这 17 条逐项相加是 213.27 小时，少算 24.72 小时；调用链里只有两个业务接口，没有任何计算工具，属于纯口算。
- 根因：`math_eval` 只在模型主动用 `tool_search` 搜索“计算”时才加载，模型看到业务数据后往往直接口算；系统提示也没有强制“合计必须走工具”。

## 修复内容

### 业务工具结果自带服务端精确统计

- 工具返回对象数组时，服务端在结果进入模型前逐字段计算条数、合计、平均、最小、最大，并在工具结果最前面注入：
  `【服务端精确字段统计｜合计、平均、条数、最大最小一律引用这里，不要从明细重算】`
- 统计放在正文之前，即使原始 JSON 很长被截断也不会丢；模型不再需要从明细重算。
- 只统计至少覆盖一半行的纯数值字段，避免把偶尔出现的编码/序号当成指标；单次最多统计 5000 行、12 个字段。

### 计算工具常驻并支持批量求和

- `math_eval` 升级为「计算与汇总」：新增 `values` 参数，一次传入整列原值（支持 `10.3`、`10.3小时`、`10:18`），返回条数、合计、平均、最小、最大；单算式继续用 `expression`。
- `math_eval` 加入核心工具，每轮对话常驻，不再依赖模型先搜索。

### 系统提示硬规则

- 回答里出现合计、总计、平均、占比、跨天或跨零点时长：能引用 `rowStats` 就直接引用，否则必须调用 `math_eval`，禁止口算、估算、先四舍五入和漏行。
- 分析、对比、排名、占比、最多/最少/平均只能基于全量数据（`rowStats` 或 `batch_read`/`batch_analyze` 结果），不能凭前几行样本下结论。
