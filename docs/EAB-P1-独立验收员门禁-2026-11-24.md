# EAB P1 · 独立验收员门禁（AGT-09）

> 日期：2026-11-24
> 对应审计项：`docs/EAB-Agent框架对照审计与能力建设需求-2026-11-23.md` 的 AGT-09
> 目标：工程任务由实现员完成后，必须经过一个没有写权限的独立验收员复核；未通过不得标记成功。

## 一、为什么需要这一层

升级前，工程子任务只检查实现员自己本轮是否跑过测试/构建并通过（`hasPassingVerification`）。这能挡住“没跑验证就说完成”，但挡不住三种更隐蔽的假成功：

- 命令跑了，但测试覆盖不到验收标准；
- 实现员只改了一半，测试却刚好只跑了一个无关用例；
- 实现员在回报里把失败解释成“环境问题”，实际没有验证目标路径。

所以 AGT-09 在“实现员自测通过”之后再加一道独立复核：换一个执行上下文、换一个模型（有可用模型时）、只给读和验证工具，让它实际去查、去跑，再提交结构化结论。

## 二、执行链路

1. 子 Agent 接到工程任务，按原有 `engineeringVerificationGate` 反复修到出现测试/构建通过证据。
2. 自测通过后，主调度不再直接标记成功，而是调用 `runIndependentCriticReview`：
   - 新建一条独立 `agent_run`，`parentRunId` 指向实现员的 run，标题为“验收员 · 任务标题”；
   - 会话使用隔离的 `agent:critic:<runId>`，不进入团队窗口，也不污染用户会话；
   - 有多个可用模型时优先选一个与实现员不同的模型，降低“同一模型自己批自己”的偏差；只有一个模型时退回该模型，不因“没有第二个模型”把任务判死。
3. 验收员拿到：原始任务要求、验收标准、实现员文字回报、实现员登记产物、最近 10 条工具与结果摘要。
4. 验收员必须实际读取文件或运行测试/构建，最后通过专用工具 `review.verdict` 提交：
   - `verdict`：`approve` / `reject`；
   - `reason`：关键依据；
   - `evidence`：至少 1 条具体证据（命令、文件路径或测试结果）。
5. 调用方从工具轨迹读取参数，而不是解析正文：
   - 最后一次 `review.verdict` 必须是 `done`；
   - 必须有 `approve|reject`、非空理由、至少 1 条证据；
   - 任何一项不满足，都按“未提交有效结论”，任务失败。
6. `approve` 才继续原有完成事件；`reject` 或 `error` 都走失败分支：
   - 任务行标 `failed`；
   - 子 Agent 收到“【独立验收未通过】…”；
   - 父 Agent 收到失败完成事件，可以决定重派或向用户说明。

## 三、数据落库

新增迁移 `packages/storage/migrations/0094_agent_task_reviews.sql`，表 `agent_task_reviews`：

| 字段 | 含义 |
| --- | --- |
| `id` | review 记录 id |
| `company_id/user_id/team_id` | 租户与团队归属 |
| `task_id` | 被验收的 `agent_tasks.id` |
| `worker_key` | 实现员团队内 key |
| `child_run_id` | 实现员 run |
| `reviewer_run_id` | 验收员 run |
| `reviewer_model_id` | 验收员模型 |
| `verdict` | `approve / reject / error` |
| `reason` | 结论理由 |
| `evidence_json` | 具体证据数组，最多 8 条 |
| `duration_ms` | 复核耗时 |
| `created_at` | 创建时间 |

同一任务允许存在多条 review：reject 后重做再验，是两条历史，不覆盖。这样控制台或审计查询能看到“失败过几次、每次卡在哪”。

## 四、工具与权限

新增内置工具 `review.verdict`：

- 入参：`verdict`、`reason`、`evidence[]`；
- 只有 `sessionId` 以 `agent:critic:` 开头的会话可以调用，普通主会话和普通子 Agent 调用会被 `FORBIDDEN` 拒绝；
- 普通 Agent 的工具目录不包含它，`tool_search` 也搜不到；只有 `allowReviewTools=true` 的验收员轮才下发。

验收员工具白名单 `AGENT_CRITIC_TOOL_NAMES`：

- `workspace.list` / `workspace.read` / `workspace.search`
- `project.exec` / `project.job`
- `office.read_outline`
- `review.verdict`

不含 `workspace.write`、`workspace.edit`、`workspace.folder`、`agent.publish_artifact`，因此验收员无法通过文件工具改代码或登记交付物。`project.exec` 仅用于跑测试/构建/核对命令，提示词明确禁止改代码；这条边界是“工具权限 + 行为约束”，不是内核级只读沙箱。

## 五、配置

新增两个可选项，均有默认值，不配置也能跑：

- `EAB_AGENT_CRITIC_MAX_ROUNDS`：验收员最多几轮模型→工具，默认 10；
- `EAB_AGENT_CRITIC_TIMEOUT_MS`：验收员整轮截止，默认 300000 ms。

超时、模型不可用、工具提交失败、没有 `review.verdict`，统一记 `verdict=error` 并让任务失败，不做“超时即放行”。

运行前提：服务必须启用 `EAB_PROJECT_EXEC=local`。这个开关同时控制 `project.exec` / `project.job` 是否下发，以及 `shouldRequireEngineeringVerification` 是否把任务判定为工程任务；关闭时 AGT-09 不会触发。本轮重启已按本地开发模式启用。

## 七、已知边界与下一步

- 当前只对 `shouldRequireEngineeringVerification` 判定为工程的任务触发；资料检索、对比、总结不额外复核。
- 验收员复用同一工作区，能看到实现员的真实文件；但 `project.exec` 不是只读沙箱，行为边界靠工具白名单 + 提示词约束。
- 复核结论已落库，但控制台任务详情页暂未展示 review 记录；下一步可在 `GET /api/console/agent-runs/:id` 增加 reviews 字段并在任务详情弹层显示“验收员 / 结论 / 证据”。
- reject 后当前不做自动重派；父 Agent 收到失败事件后决定是否重做，避免同一任务无限“改—验—拒”循环。
