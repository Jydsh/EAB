## 0. 一页结论

**EAB 已经不是 “从零起步” 的项目。** 现有代码是一个可运行的企业受控 Agent 运行时：有模型路由、工具目录、知识库、四层上下文、持久化团队、MCP/A2A 适配、审批流、审计和配额。项目规则里 “目前什么都没有、从零开发” 的描述需要校正；后续应当**增量演进，不建议推翻重写**，否则会丢掉已经沉淀的权限、工具和团队能力。

按这套 Agent 框架逐项对照，结论分三层：



1. **“能不能用”：已经达标。** 单轮企业问答、知识库检索、文件 / Office 操作、业务接口调用、日程 / 定时任务、多 Agent 派活、钉钉 / 飞书渠道，都有真实链路。

2. **“好不好用”：部分达标。** 复杂任务能拆、能派、能收，但计划还不是一等对象，执行没有硬预算，验收主要靠提示词和父 Agent 自觉，提示规则重复且过长。

3. **“可不可信”：还没达标。** 当前只能证明 “调用过工具”，不能证明 “答案里的数字来自这次工具结果”；没有任务级评测集，工具风险和沙箱边界也不完整。

一句话判断：

> **EAB 是一个 “能力很全、治理骨架已经成形” 的企业 Agent 基座，但还不是一个 “答案可验证、执行可预算、效果可度量” 的数字员工平台。**

按 31 个框架检查点，当前大致是：



| 判定           | 数量 | 含义                     |
| ------------ | -- | ---------------------- |
| A：已实现并接入     | 12 | 代码里有、主链路在用、有测试或真实会话证据  |
| B：部分实现 / 有条件 | 15 | 有能力，但缺硬约束、缺评测、或缺最后一段闭环 |
| C：未实现        | 2  | 生活服务覆盖、任务级评测体系         |
| D：当前明确不需要    | 2  | ToT 树搜索、模型微调           |

> 说明：这不是 “打分越高越好” 的考试。企业 Agent 的关键不是把 31 项全做满，而是把 “正确性、可控性、可评测” 做成硬约束。ToT 和微调现在做，收益大概率小于成本。

### 1.3 先校正三处 “文档比代码跑得快”

这三处会直接误导后续判断，建议先改文档，再谈开发：



1. **总体架构里的&#x20;**`ToolDescriptor`**&#x20;比代码完整。** 架构写了 `risk`、`dataEffect`、`approval`、`audit` 等字段；实际 `routes/tools.ts` 的 `ToolDef` 主要是 `scope`、`dangerous`、`concurrency`、`lockKey`、`idempotent`。通用 “风险分级 + 逐次审批” 并没有按架构完整落地。

## 3. 现在的 EAB 到底 “遵循” 了多少

### 3.1 已经真正遵循的部分

这些不是纸面能力，主链路已经在用：



1. **LLM 作为决策核心**：多 Provider、多模型、用途路由、健康检查、速度选模。

2. **工具调用闭环**：模型选工具、参数校验、执行、结果回填、失败重试、审计。

3. **RAG 主链路**：关键词 + 向量 + RRF + rerank + ACL，不是 “只做关键词”。

4. **上下文分层**：短期原文、会话摘要、长期记忆、按需历史召回、知识库资料分层。

5. **多 Agent 经理制**：主 Agent 编队、子 Agent 执行、父子问答、后台唤醒、产物交接。

6. **企业治理骨架**：公司隔离、角色权限、工具 scope、插件隔离、配额、审计、审批流。

7. **模型能力匹配**：按任务能力选视觉 / 聊天模型，子 Agent 按负载分散模型。

### 3.2 只是 “有条件遵循” 的部分

这些能力存在，但还不是硬约束：



* **提示词工程**：有分层，但规则重复、单文件拼装、无版本。

* **计划执行**：有任务和验收，没有 Plan 对象和步骤状态。

* **长期记忆**：有确认机制，但没有类型、衰减、冲突和向量召回。

* **多 Agent 角色**：有岗位卡，但工具边界没有按卡强制执行。

* **工具权限**：有 scope 和危险工具排除，但没有通用风险分级和逐次审批。

* **工作流**：有审批流和定时任务，没有通用业务任务图。

* **部署**：单机可跑，没有容器化和多实例。

### 3.3 还没有真正做的部分



* **任务级评测体系**：没有 golden set、没有发版闸门。

* **答案事实校验**：没有 “数字 / 名单必须能在工具结果里找到” 的硬校验。

* **生活服务**：只有天气和浏览器，不是当前重点。

### 3.4 明确建议现在不做的部分



* **ToT 树搜索**：当前任务类型不需要；先做 “计划 + 验收”，比做树搜索收益大。

* **模型微调**：没有评测集之前不做；先把 RAG、提示词和 eval 做扎实。

## 4. 比通用框架更好的地方（不要丢）

EAB 有不少东西是 LangChain/CrewAI 这类通用框架不会直接给的，重构时不能当 “技术债” 扔掉：



1. **企业治理是内建的**：公司隔离、部门、角色、scope、配额、审计、审批，不是后贴的。

2. **工具目录是运营化的**：`tool_search`、能力索引、按需加载 schema、角色白名单、并发锁、幂等、审计。

3. **知识库不是 “向量玩具”**：有解析、清洗、切片、关键词、向量、RRF、rerank、ACL、召回测试。

4. **多 Agent 是持久化团队**：有任务、产物、父子问答、后台唤醒、检查点，不是一次性对话。

5. **上下文有工程约束**：分层、预算、截断、批次分析，不是把历史无限塞。

6. **模型有路由和健康**：用途路由、能力匹配、速度选模、失败归因。

7. **插件有进程隔离**：默认进程外 + 能力令牌 + 双重校验，这比 “所有工具一个进程” 安全。

这些是 EAB 的护城河。优化应当 “在骨架上加约束”，不是 “换一套骨架”。

## 6. 优化方向：在现有骨架上加 “五条硬约束”

### 6.1 把 “计划” 变成一等对象

现在 EAB 的计划藏在模型输出和团队任务描述里。建议加一个轻量 `Plan` 对象，不引入复杂工作流引擎：



```
Plan {
  goal, constraints[], steps[],
  step: { id, owner, status, inputRefs[], outputRefs[], acceptance, budget }
}
```

最小落地：



* 复杂任务先产出 1 份计划，最多 7 步；简单任务不强制。

* 每一步有 `pending/running/blocked/done/failed`，父 Agent 可以展示 “做到第几步”。

* 计划可被用户修改一次；修改后版本化。

* 计划不是提示词，是数据库对象，能回放、能审计。

这解决的是 “看起来很忙，但不知道做到哪” 的问题。

### 6.2 加 “证据账本”，把答案正确性做成硬校验

当前门禁是 “有一次成功、带参、有返回的取数调用”。下一步要加：



* **事实账本**：每次工具结果抽取可核对的事实：人名、日期、金额、合计、条数、状态、文档标题、页码。

* **答案校验**：最终回答里的关键数字 / 名单，必须能在账本里找到；找不到就拦一次，要求核对或改成 “未查到”。

* **引用绑定**：知识库回答必须带文档标题 + 片段 / 页码；业务数据回答必须带 “查询口径 + 数据来源”。

* **无证据降级**：没有证据时明确说 “查不到 / 工具不可用”，不允许用记忆和估计补齐。

这不是 “再加一条提示”，而是服务端校验。提示只能降低概率，校验才能拦住。

### 6.3 做 Prompt Compiler，不再在 `chat.ts` 里拼字符串

建议把系统提示拆成固定六段，按优先级装配：



1. 身份与边界

2. 本轮唯一任务

3. 工具与数据规则（只保留一份）

4. 计划 / 执行 / 验收规则（复杂任务才注入）

5. 记忆与知识库使用规则

6. 输出格式与禁止项

要求：



* 每段有 ID、版本、token 预算、适用场景。

* 同一规则只出现一次；工具侧能校验的，不写进提示。

* 每次运行快照实际使用的 prompt 版本和字符数。

* 建 10–20 条 “提示回归题”，改提示必须跑。

这能同时解决 “规则重复、思考复述、提示词不可维护” 三个问题。

### 6.4 工具风险分级 + 沙箱 + 逐次审批

建议把工具按四档分级：



| 风险档     | 例子                          | 默认策略              |
| ------- | --------------------------- | ----------------- |
| 只读      | 搜索、知识库、读文件、查天气              | 允许，记审计            |
| 低写      | 写个人文件、建日程                   | 允许，记审计，可撤销        |
| 高写      | 发消息、发邮件、改业务数据、删文件           | 逐次确认或按策略审批        |
| 执行 / 外部 | `project.exec`、浏览器下单、远程 A2A | 强制沙箱 / 白名单 / 人工确认 |

重点补三件事：



* `project.exec` 进入容器或受限 shell；至少做命令白名单、工作区只读挂载、网络出口控制。

* 通用写工具补 `risk`、`dataEffect`、`approval` 字段，审批绑定本次 `tool_call` 参数哈希，不能复用。

* 审批拒绝后不自动换工具重试；这是安全策略，不是 “再试一次”。

### 6.5 记忆 OS：先分类型，再谈向量

当前记忆只有一段 `content`。建议至少分四类：



* `preference`：用户偏好（回复语言、格式、常用口径）

* `fact`：稳定事实（部门、岗位、常用项目）

* `decision`：已确认的决策 / 口径

* `episode`：一次任务的经验（可衰减）

规则：



* 用户偏好和个人事实必须用户确认；团队规则必须管理员确认。

* 冲突时新记忆不能静默覆盖旧记忆，要标 “冲突待确认”。

* 召回从纯词面升级为 “词面 + 向量” 混合；先小规模，不必上独立向量库。

* 情景记忆加时间衰减；偏好和决策不衰减。

### 6.6 多 Agent 从 “角色扮演” 升级为 “能力契约”

现在五张岗位卡已经存在，但 `tools` 只是摘要。建议：



* 子 Agent 启动时按 `AgentCard.tools` 生成硬 allowlist；卡外工具直接不可见。

* `TaskBudget` 从 “记录” 变成 “硬停”：token / 时长 / 费用任一超限，任务进入 `failed/budget_exceeded`，父 Agent 收到原因。

* 验收员必须独立：实现任务完成后，由一个没有写权限的 `critic` 复核产物 / 测试结果；不能由实现者自评。

* 编队加复杂度门禁：单步事实问答、单文件读取不强制团队；只有可拆分、可并行、可独立验收的任务才派 2–4 个。

* 产物交接带 `artifactId + checksum + preview + mime`，父 Agent 不重复读全文。

### 6.7 工作流：复用审批流引擎，不另起一套

`approval-workflows.ts` 已经有流程 JSON、版本、发布、校验、节点。它现在只服务审批，但骨架可以复用：



* 抽象 `WorkflowDefinition`：节点、依赖、条件、重试、人工确认、超时。

* 先做 “任务图 v1”：线性 + 分支 + 人工节点，不做拖拽画布。

* 每个节点可以是工具、子 Agent、人工审批、等待。

* 版本化、可回放、可按 `traceId` 查每次执行。

* 可视化放 P2；先把 “能定义、能跑、能查” 做出来。

不要现在做 “大而全的低代码工作流平台”。先把计划、任务、验收跑通。

### 6.8 评测与可观测：没有度量，就不要谈优化

建议先做 30 条真实业务题，不求多，求可重复：



* 覆盖：加班 / 考勤、问卷 / 名单、制度条款、文件 / 表格、知识库问答、多步办公任务。

* 每条有：标准答案、必须出现的证据、禁止出现的内容、允许的工具集合。

* 每次发版跑：任务完成率、工具调用成功率、参数正确率、数字一致率、无依据数字数、平均轮次、P95 耗时、token 成本。

* 规则校验 + 小模型裁判结合；不要完全依赖 LLM 打分。

可观测补一个 “任务详情页”：



* 父子 Agent 树

* 每步工具、参数、结果摘要、耗时

* token / 费用

* 计划步骤状态

* 失败原因和重试次数

## 8. 建议的实施顺序（单人 + AI 的现实节奏）

### 阶段 1：可信回答（2–3 周）

目标：员工敢用，数字敢信。
