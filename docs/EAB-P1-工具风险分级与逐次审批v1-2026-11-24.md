# EAB P1 · 工具风险分级与逐次审批 v1

- 日期：2026-11-24
- 对应需求：审计表 AGT-05「工具风险分级 + 逐次审批」
- 验收口径：高风险工具在真实执行前必须有一张可审计、与参数绑定、只能使用一次的审批；`project.exec` 先做受限执行，完整 OS 沙箱拆为 AGT-05b
- 版本：沿用当前 `2026.11.23.04`，本次未改版本号

## 1. 这一版解决什么问题

原来的 `ToolDef` 只有 `dangerous` 布尔值和 `concurrency`，导致两个极端：

- 所有工具都没有统一风险等级，控制台无法解释“为什么这个工具危险”；
- 高危二次确认只覆盖零散分支，`project.exec` 这类命令执行没有统一门禁，模型误调一次就可能直接跑在本机上。

AGT-05 把“风险分级”和“审批”拆成两层：风险等级决定展示与策略，审批负责真实拦截。审批不是前端弹窗装饰，而是**执行前的服务端门禁**；没有审批通过，工具函数根本不会被调用。

## 2. 风险分级

核心文件：`packages/server/src/tool-approval.ts`

四档风险：

| 风险 | 含义 | 典型工具 |
| --- | --- | --- |
| `read` | 只读，不改状态 | `workspace.read`、`web.search`、`kb.search` |
| `write` | 可恢复的写入 | `workspace.write`、`workspace.edit`、`office.insert` |
| `exec` | 在本机执行命令或驱动外部运行时 | `project.exec`、`project.job`、`plugin.dev`、`skill.dev`、`browser`、`browser.use` |
| `irreversible` | 删除、改密、外发等难以撤回的动作 | `workspace.delete`、`admin.password.reset`、`workspace.send_dingtalk` |

高风险写入集合：`office.rewrite / office.format / office.versions / workspace.rename`。这些工具本身是 `write`，但会整篇覆盖或改结构，按“高风险写入”要求审批。

优先级：

1. 工具定义里显式写了 `risk` 就用它；
2. 否则按执行类、不可逆类、高风险写入集合匹配；
3. 再按 `dangerous`、`concurrency='exclusive'`、`concurrency='write'` 兜底；
4. 其余为 `read`。

审批策略：

- `exec`、`irreversible`、高风险写入 → `always`；
- 普通 `write`、`read` → `never`，只写审计，不逐次弹窗。

这样普通写文件、普通 Office 编辑不会被审批淹没；真正危险的动作才需要人确认。

### 2.1 分支级审批

同一个工具里不是每个 action 都有副作用，所以支持按参数分支：

| 工具 | 需要审批的 action | 不需要审批的 action |
| --- | --- | --- |
| `project.job` | `kill` | `output`、`list` |
| `office.versions` | `restore` | `list` |
| `workspace.folder` | `delete` | `create`、`rename` |

`workspace.folder action=delete` 会递归软删本人文件，已补为逐次审批；创建和重命名不打扰。

## 3. 审批单

复用现有 `approvals` 表，新增迁移：

`packages/storage/migrations/0101_tool_approval_used.sql`

```sql
ALTER TABLE approvals ADD COLUMN used_at INTEGER;
```

关键字段语义：

| 字段 | 含义 |
| --- | --- |
| `action` | `tool:<toolId>`，同一工具的动作固定 |
| `resource_type` | `tool` |
| `resource_id` | 工具参数的 SHA-256 摘要（`toolArgsDigest`） |
| `payload_json` | 工具名、风险、参数摘要、消息/会话/运行 id |
| `status` | `pending / approved / rejected / expired` |
| `expires_at` | 审批有效期，默认 5 分钟 |
| `used_at` | 被哪次执行消费；为空表示尚未执行 |

参数绑定：`toolArgsDigest` 用规范化 JSON（键排序、去掉 `undefined`）再做 SHA-256。换参数、换路径、换命令都无法复用同一张审批。

待办复用：同公司、同申请人、同 action、同参数哈希的 `pending` 会被复用，避免模型连续重试时刷出多张单。并发插入撞唯一索引时回查已有记录。

一次性核销：

```sql
UPDATE approvals
SET used_at = ?
WHERE id = ? AND company_id = ? AND status = 'approved' AND used_at IS NULL
```

条件更新只有第一次能成功。第二次带同一个 `approvalId` 重试会得到 `EAB_CONFLICT`，不会再次执行。

## 4. 执行门禁

`packages/server/src/routes/tools.ts` 的 `executeTool` 在“空间校验之后、并发名额和资源锁之前”调用审批门禁。

顺序很重要：审批等待不占工具槽位，也不持资源锁，否则一个人等审批会把全公司的同名工具锁死。

三种模式：

| 模式 | 行为 | 使用场景 |
| --- | --- | --- |
| `wait` | 生成待办，回调入口投递审批卡，轮询到 approved / rejected / expired；通过后先核销再执行 | 网页流式聊天、钉钉私聊 |
| `defer` | 生成待办后抛 `EAB_APPROVAL_REQUIRED`（HTTP 202），带 `approvalId` | 直接工具 API、非流式聊天、飞书 |
| `bypass` | 跳过审批 | 测试环境；已完成人工确认的任务图节点 |

默认策略：

- 显式 `context.approval` 优先；
- `NODE_ENV === 'test'` 默认 `bypass`，避免测试被审批卡住；
- 生产默认 `defer`，没有审批就不执行。

带 `approvalId` 重试时校验：

1. 审批存在且属于同公司、同申请人；
2. `action` 与当前工具匹配；
3. `resource_id` 与当前参数哈希一致；
4. `status='approved'`；
5. 未过期；
6. `used_at` 为空。

任一条不满足都拒绝，并提示重新发起调用。

## 5. 聊天接入

```ts
}
```

该事件加入 Redis 跨实例广播白名单，多实例下审批卡也能推到申请人所在实例。

### 5.1 钉钉渠道

新增 `packages/server/src/tool-approval-dingtalk.ts`。

- 钉钉私聊遇到高危工具时，`runAgentTurn` 用 `wait` 模式执行，`onToolApprovalPending` 在等待前投递 A2UI 审批卡；
- 申请人自己有 `approval:decide` 时，卡发给申请人；否则查同公司拥有 `approval:decide` 且角色未过期的活跃成员，最多发 5 张，任意一人通过即可；
- 卡按钮 `allow` / `reject` 带 `sessionId=toolapproval:<approvalId>`，回调先校验钉钉绑定、成员状态、审批权限、pending 状态和过期时间；
- 回调用 `WHERE status='pending'` 条件更新，两个管理员同时点只有一张生效；生效后异步把原卡收口成“已允许 / 已拒绝 / 已过期 / 已被他人处理”；
- 如果一张卡都没送达，`onPending` 返回 `false`，`wait` 立即抛 202 并保留控制台待办，不让本轮空等 120 秒；
- 审批结果仍写 `tool.approval.approved / rejected` 审计，并复用网页 SSE 通知申请人。

边界：卡片本身不落库，进程重启后旧卡不再自动刷新；审批单仍在 `approvals` 表里，管理员可以从控制台继续处理。当前等待窗口是 120 秒，审批单有效期是 5 分钟；超过等待窗口后工具会返回“等待审批超时”，需要重新发起。

审批决策接口：

`POST /api/chat/tool-approvals/:id/decide`

- 需要 `approval:decide` 权限；普通员工 403；
- 只允许 `pending` 改 `approved / rejected`；
- 检查过期，过期先落 `expired` 再返回 409；
- 写 `tool.approval.approved / rejected` 审计；
- 决策后向申请人发布审批结果 SSE，网页卡片不会停在“待处理”。

控制台仍用同一张 `approvals` 表：

- `GET /api/console/approvals` 返回 `usedAt`；
- `POST /api/console/approvals/:id/decide` 决策后同样发 SSE；
- 决策时先检查 `expires_at`，过期直接落 `expired` 并返回 409；
- 状态更新带 `WHERE status='pending'`，两个管理员同时点只有一个成功；
- 控制台列表在 `usedAt` 存在时显示“已执行”，否则显示原状态。

## 8. 审计

写入哈希链 `audit_logs` 的动作：

| 动作 | 时机 |
| --- | --- |
| `tool.approval.requested` | 生成待办时，结果记为 `deny` |
| `tool.approval.allowed` | `wait` 模式通过并核销后 |
| `tool.approval.approved` | 管理员通过 |
| `tool.approval.rejected` | 管理员拒绝 |

审计失败只告警，不回滚审批或工具执行；审批表本身仍是权威状态。
