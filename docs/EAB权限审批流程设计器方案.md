## 一、结论摘要

这次不是给现有审批页换皮，而是把“权限申请”从**角色白名单里的临时授权**，改成**面向全部权限点的正式审批流程**：

1. 申请人可以申请公司权限目录里的所有权限点，不再受“哪些角色可申请”限制。
2. 审批通过后，权限只写入**申请人个人**的 `permission_scope_grants`，不写 `role_scopes`、不改变共享角色。
3. 成员有多个当前角色时，申请页要求选择一个角色作为**申请身份与审批策略上下文**；该角色不因审批通过而获得新权限。
4. 任一级驳回、流程超时、申请人撤回或申请人离职/禁用时，不授权，并向申请人发送“审批未通过”的通知。
5. 管理端从“策略表单”升级为**可视化流程设计器**：模板列表、流程画布、节点属性面板、条件分支、审批人配置、转交、加签、抄送、发布与版本管理。
6. 页面信息架构重做：管理端分为「流程设计」「审批记录」「权限目录」；员工端申请改为“权限目录多选 + 当前角色选择 + 审批路径预览 + 有效期”。

> 重要澄清：最初提出的“审批通过加到成员当前角色”会让该角色下所有成员获得权限。例如“普通员工”当前有 151 人，任何一人获批，151 人都会获得。你已确认改为**只给申请人个人授权**，因此本方案不改共享角色，避免这种连带授权。

## 二、现状问题

### 2.1 现有页面

当前 `/admin` → 组织与权限 → 权限审批 页面由三块组成：

- 顶部 1-2-3 流程说明；
- “开放申请的角色”复选框；
- “审批链策略”表单 + 策略表格。

它回答的是“管理员怎么配置规则”，而不是“一个权限申请会经过哪些节点、每个节点谁审批、什么条件走哪个分支”。这与氚云式流程设计器的操作心智不一致。

### 2.2 现有实现与需求的冲突

| 现状 | 新需求 | 影响 |
|---|---|---|
| 可申请范围只来自 `requestable=1` 的非管理角色 | 申请全部权限点 | 需要废弃角色白名单对申请范围的限制 |
| 审批通过写 `permission_scope_grants`，只对申请人生效、按有效期失效 | 仍写 `permission_scope_grants`，只给申请人个人授权 | 保留个人临时授权模型，不写共享角色 |
| 审批链是“部门负责人链 / 固定审批人 / 公司管理员兜底”自动生成 | 可视化流程设计，节点、条件、分支可配 | 需要新的流程模板、版本和运行时快照 |
| 管理端只有策略表单 | 模板列表 + 画布 + 属性面板 + 发布 | 页面信息架构和交互全部重做 |
| 拒绝只更新钉钉审批卡，不主动通知申请人 | 对话页或钉钉机器人回复申请人 | 需要申请人通知通道、模板、重试与去重 |
| 只支持顺序步骤 | 条件分支、会签/或签、转交、加签、抄送、通知节点 | 步骤表需要节点、分支、并行组、审批动作语义 |

### 2.3 可复用能力

- 现有 `permission_requests`、`permission_approval_steps`、`permission_request_decisions` 的状态机与幂等思路。
- 钉钉 A2UI 审批卡的落库、主动投递、回调校验、失败重发。
- `departments.manager_user_id` 的部门负责人链。
- `roles` / `role_scopes` / `user_roles` 的角色权限模型。
- 控制台现有的角色、成员、权限目录接口与视觉体系。

## 三、新需求定义

### 3.1 申请对象：全部权限点

- 数据源改为 `SCOPE_REGISTRY` 的全部已登记权限点，不再从 `requestable` 角色反推。
- 员工端按业务分组展示，例如“对话与 Agent”“知识库”“组织与权限”“系统与运维”。
- 已被当前身份拥有的权限点置灰，标注“已拥有”，不可重复申请。
- 支持一次申请多个权限点，合并为一张申请单。
- 多选权限时，按流程模板匹配规则决定走哪条流程；如果多个权限命中不同流程，默认拆成多张单，或在申请页提示“将拆分为 N 张审批单”。不允许静默合并到某一条流程。
- 权限目录中的管理类、危险类权限不做硬编码隐藏，但必须命中“高敏权限流程”，流程至少包含企业级管理员节点。这样既满足“所有权限可申请”，又不把提权变成绕过审批的通道。

### 3.2 申请角色：选择一个当前角色（不改角色）

申请单保留“申请角色”字段，它的语义是**申请身份与审批策略上下文**，不是授权落点：

- 成员当前只有一个有效角色：自动带入该角色，页面只读展示。
- 成员当前有多个有效角色：要求申请人从自己的当前角色中选择一个，不能选择自己未持有的角色。
- 申请角色必须是有效、未删除、未过期的 `user_roles`。
- 申请页展示角色名称、编码，并明确提示：“当前角色用于审批策略匹配和申请身份记录；审批通过只给你本人授权，不会改变该角色，也不会给角色下其他成员授权。”
- 审批单保存角色快照，用于流程匹配、审批人解析和审计。
- 审批期间角色发生变化时，已发起的申请继续按快照跑完；最终授权只校验申请人仍在职、未禁用、同公司，不要求仍持有该角色。
- 个人授权模式不写 `role_scopes`、不写 `user_roles`，不产生共享角色变更。

### 3.3 审批通过：写入申请人个人授权

最终一级通过后，在同一个事务内完成：

1. 校验申请人仍在本公司、在职、未禁用。
2. 校验审批单仍为 `pending`，所有必需节点已完成。
3. 按获批权限点逐条写入 `permission_scope_grants`：
   - `request_id`、`company_id`、`user_id`、`scope` 唯一；
   - `granted_by` 记录最终审批人；
   - `expires_at = 通过时间 + 申请有效期`。
4. 审批单置为 `approved`，记录 `granted_scopes_json` 和 `granted_at`。
5. 写审计：申请单、申请人、权限清单、有效期、最终审批人。
6. 通知申请人：“审批已通过，权限已授予你本人，有效期至 X。”

幂等要求：

- 同一申请单重复回调、重复点击不能重复写 `permission_scope_grants`。
- `(request_id, scope)` 唯一约束兜底；已存在时按幂等成功处理。
- 授权失败时审批单不能显示“已通过”；落为 `grant_failed` 并进入人工处理队列。
- 不写 `role_scopes`，不写 `user_roles`，不触发角色下其他成员权限变化。

个人授权的生效范围：

- 默认有效期 7 天，最大 30 天，沿用现有 `durationHours` 语义。
- 到期后读侧按 `expires_at` 过滤，记录保留用于审计。
- 管理员可提前撤销个人授权，写 `revoked_at` 并审计。
- 如果未来需要“角色模板变更”，作为独立功能另做，不与本审批流混用。

### 3.4 驳回、超时、撤回：通知申请人

触发条件：

- 任一级审批人拒绝；
- 审批流程超时；
- 申请人主动撤回（可选通知，默认不通知本人）；
- 申请人离职/禁用或授权写入失败导致无法授权。

通知内容至少包含：

- 申请单号；
- 申请权限摘要；
- 结果：未通过 / 已超时 / 已撤回 / 角色失效；
- 拒绝节点、审批人、审批意见；
- 发生时间；
- 操作入口：查看详情、重新申请。

通知渠道：

1. **对话页**：在员工端“系统通知”会话或消息中心生成一条审批结果卡片，带未读标记；点击打开审批详情。
2. **钉钉机器人**：如果申请人已绑定钉钉且公司渠道可用，向申请人私聊发送文本或 A2UI 结果卡。
3. 两个渠道都可用时默认双发；任一渠道失败不阻断审批状态，进入通知重试队列。
4. 同一申请单同一结果只发一次，使用 `notification_key` 去重。
5. 审批通过也建议发送同结构通知，避免“只有失败才有人管”的体验断裂。

### 3.5 安全边界

- 只能本人申请，不能代申请。
- 审批人每级重新校验：在职、同公司、步骤仍为当前节点、拥有 `approval:decide`、不是申请人本人。
- 固定审批人、角色审批人、部门负责人都必须在运行时解析成真实成员，并校验权限；解析不到时按节点“空节点策略”处理。
- 管理类权限（如 `authz:grant`、`approval:decide`、系统更新、审计导出）必须命中高敏流程，流程中至少一个节点为企业级管理员或平台超管。
- 流程发布前必须通过校验：开始节点唯一、结束节点可达、审批节点有审批人、条件分支有兜底分支、环检测、空节点策略明确。
- 所有流程发布、申请、审批、授权、回滚、通知都写审计。

## 四、可视化流程设计器

### 4.1 设计目标

对齐氚云式流程设计器的核心体验，而不是做一个“字段更多的表单”：

- 左侧：流程模板列表，可搜索、复制、启用/停用、新建。
- 中间：自由流程画布，节点可点击、可拖动到任意位置，画布支持滚轮缩放、空白平移、适应画布、自动布局、专注画布和右键建节点；节点上/下/左/右四个端口均可拖到任意节点创建连线，支持多条出线、跨层跳转、分支汇合和条件自由出线；选中连线后两端手柄可分别重连起点/终点。
- 右侧：选中节点或连线后的属性面板，节点配置审批人、审批方式、条件、超时、通知；连线配置标签、条件规则或删除。
- 顶部：流程名称、适用范围、状态（草稿/已发布）、模式徽标、保存草稿、校验、发布。
- 发布后生成版本快照；运行中的申请使用发起时的版本，不受后续编辑影响。
- 当前自由画布是**显式边拓扑**：节点逻辑关系以 `nextIds` 为准，`edgeLabels / edgeRules` 保存连线标签与条件规则；旧 `flow` 数组和 `branches` 仍可读取，首次编辑连线时物化为显式边。连线是建边而非调序，允许审批节点多出线、跨分支汇合；开始节点只允许 1 条出线，结束节点只允许连接到抄送节点，抄送节点可作为末端且允许没有出线，禁止环。

### 4.2 节点类型

完整版支持以下节点：

| 节点 | 作用 | 关键配置 |
|---|---|---|
| 开始 | 申请单进入流程 | 适用权限范围、适用角色、适用部门 |
| 审批 | 一个人或一组人审批 | 审批人来源、审批方式、超时、空节点策略、转交/加签权限 |
| 条件 | 按条件走不同分支 | 权限分组、危险级别、申请角色、部门、申请时长 |
| 通知 | 向指定对象发消息 | 通知对象、渠道、模板 |
| 抄送 | 知会相关人，不参与审批 | 抄送对象、渠道、模板、是否允许查看详情 |
| 结束 | 通过/拒绝收口 | 通过动作、拒绝动作、通知对象 |

审批人来源：

- 直属上级 / 部门负责人链（1–10 级，逐级向上；申请人本人是部门负责人时从上级部门开始；上级部门无负责人时跳过该级；节点未关闭兜底时才由公司管理员补位）；
- 指定成员；
- 指定角色（该角色所有有 `approval:decide` 的成员）。角色选择弹窗会列出当前公司全部角色，但只有同时具备 `approval:decide` 且有在职成员的角色可选；其余角色灰显并写明原因（“未开通‘审批决定’权限”或“暂无在职成员”），避免只显示两个角色时误以为角色数据缺失。
- 企业级管理员 / 平台超管。

审批方式：

- 依次审批（串行）；
- 或签（任一审批人同意即通过）；
- 会签（全部审批人同意才通过）。

审批节点的操作能力（完整版）：

- **转交**：当前审批人把当前节点转给另一名符合条件的审批人；原审批人变为“已转交”，新审批人收到新卡；转交链最多 3 次，防止踢皮球。
- **加签**：当前审批人可在自己之前或之后追加审批人；前加签先审，后加签后审；加签人必须拥有 `approval:decide`，且不能是申请人。
- **抄送**：审批完成后或到达指定节点时，向相关人发送只读通知，不产生审批步骤、不阻塞流程。
- **撤回**：申请人可在首个审批节点处理前撤回；已进入审批后是否允许撤回复审，作为流程级配置，默认不允许。

或签/会签实现建议：

- 画布上用一个审批节点表示，属性面板配置审批人集合与 `single / any / all`。
- 运行时按 `parallel_group` 生成同组步骤；或签任一步通过则其余 `skipped`；会签全部通过才进入下一节点。
- 任一拒绝即整单拒绝，未处理步骤置为 `skipped`。

### 4.3 条件分支

条件节点至少支持：

- 按权限点或权限分组；
- 按危险级别（普通 / 敏感 / 管理类）；
- 按申请人选择的当前角色；
- 按申请人部门；
- 按申请权限数量；
- 默认兜底分支。

示例：

```
开始
  └─ 条件：是否包含管理类权限？
       ├─ 是 → 企业级管理员审批 → 平台超管审批 → 结束
       └─ 否 → 部门负责人链审批 → 结束
```

### 4.4 模板匹配与版本

- 公司至少有一个默认流程，覆盖未被其他模板命中的申请。
- 支持按权限分组、权限点、申请角色、部门配置多个模板。
- 匹配优先级：精确权限点 > 权限分组 > 申请角色 > 默认流程。
- 同一优先级命中多个模板时，发布时必须阻止，要求管理员合并或调整优先级。
- 新申请创建时写入 `workflow_id` 与 `workflow_version`，流程运行期间不跟随草稿变化。
- 已发布流程可停用，但已发起的申请继续按旧版本跑完。

### 4.5 运行时步骤

- 创建申请时根据模板实例化步骤/节点，保存 `node_id`、`node_name`、`node_type`、`approval_mode`、`branch_key`、`parallel_group`。
- 直属上级 / 部门负责人链按节点 `maxLevels` 截取实际可用负责人；1 级是申请人直属上级，申请人本人是所在部门负责人时跳过本人从上级部门开始；上级部门没有负责人时跳过该级继续向上，不生成空步骤；节点关闭 `fallbackAdmin` 时不追加公司管理员，未配置时回落到默认审批链 `maxLevels` 和 `includeCompanyAdmin`。
- 审批节点完成后，按连线计算下一节点；条件节点只做路由，不产生审批步骤。
- 或签节点：任一审批人同意，其余同组步骤置为 `skipped`；会签节点：全部同意才通过，任一拒绝则整单拒绝。
- 通知/抄送节点是副作用，不阻塞主流程；失败进入通知重试队列。
- 超时按节点配置计算，超时后按节点策略处理：拒绝、转交、升级到上一级、或跳过。
- 转交在当前步骤内追加一条 `transfer` 动作，步骤保留原审批人并记录 `delegated_from`，新审批人收到新卡；转交后原审批人的卡更新为“已转交”。
- 加签在当前节点内追加一条 `add_sign` 动作，记录 `added_by`、`position`（before/after）；前加签先完成再加签，后加签在当前审批人同意后激活。
- 抄送不产生 `permission_approval_steps`，只写通知记录和详情时间线；抄送对象可以是成员、角色、部门负责人。
- 审批动作统一写 `approval_step_actions` 审计表，保留动作类型、操作人、目标人、意见、时间，保证转交/加签可追溯。

### 4.6 自由连线模型

节点结构新增四组可选字段，向后兼容旧模板：

```ts
type EdgePortSide = 'top' | 'bottom' | 'left' | 'right'
type ApprovalFlowNode = {
  id: string
  kind: 'start' | 'approval' | 'condition' | 'cc' | 'end'
  nextIds?: string[]                 // 出线目标，按数组顺序解释
  edgeLabels?: Record<string, string> // toNodeId -> 连线/分支名
  edgeRules?: Record<string, { field?: string; op?: string; value?: string }>
  edgePorts?: Record<string, { from?: EdgePortSide; to?: EdgePortSide }>
  // ...旧字段 x / y / approvers / branches 等保持不变
}
```

- **显式边模式**：任一节点出现 `nextIds` 即视为显式边模式；整张流程只按 `nextIds` 渲染、编辑和校验，旧的 `flow` 相邻数组和 `branches` 嵌套不再参与拓扑。
- **兼容模式**：没有 `nextIds` 的旧模板继续按 `flow` 数组顺序 + `branches` 嵌套生成边；首次拖动端口建线时，前端把全部旧边物化为 `nextIds`，并为旧条件分支补齐 `edgeLabels / edgeRules`。
- **四向端口**：每个节点渲染上/下/左/右四个端口；开始/审批/条件/抄送节点四向均可出线，结束节点四向同样可出线，但连线目标只能是抄送节点。端口常显低透明，选中节点时提高对比；同一侧出线多于 1 条时，端口旁显示数量角标。
- **端口持久化**：`edgePorts[toNodeId]` 保存这条边实际使用的起点侧和终点侧；没有记录时按源/目标节点中心相对位置自动选侧（上下优先，其次左右）。显式记录优先于自动推导；自动布局只改坐标，不清除已记录的端口侧。后端校验 `edgePorts` 的键必须对应真实出线，`from / to` 只能是 `top / bottom / left / right`，草稿保存后回读保留，发布时非法端口会拒绝。
- **建边规则**：禁止自连、重复出线、空目标；开始节点必须且只能有 1 条出线；结束节点可以没有出线，若有出线则每条目标都必须是抄送节点；抄送节点允许没有出线；除结束、抄送外节点必须有出线；条件节点至少 2 条出线，每条出线必须有非空且唯一的分支名和条件规则，`else` 最多 1 条；显式图必须从开始节点可达所有节点，且不能成环。
- **拖拽建边与磁吸**：从任一端口按下并拖动即开始建边；落点优先精确命中节点端口，否则在 34px 屏幕距离内磁吸最近节点并选择最近侧。合法落点显示绿色对勾与目标侧高亮，非法落点（自连、重复、开始多出线、成环、结束节点连到非抄送节点）显示灰色禁止标记并给出原因；拖到空白取消。
- **端点手柄重连**：选中连线后，在起点、终点端口位置显示 12px 圆点手柄（28px 命中区）。拖起点手柄更换源节点，拖终点手柄更换目标节点；重连保留原连线标签、条件规则和已记录的端口侧。条件边的目标重连保留原分支名与规则；普通边改接到条件源时自动生成唯一分支，条件源改接到普通源时清空该边规则。结束节点作为源节点时，新目标同样只能是抄送节点。
- **拖空白删除与撤销**：把手柄拖到空白区域即删除该连线，顶部 Toast 给出 6.5 秒“撤销”；撤销恢复删除前的完整流程快照（含 `nextIds / edgeLabels / edgeRules / edgePorts` 和节点坐标）。右侧连线属性面板和右键菜单仍可直接删除。
- **同侧多线分道**：同一节点同一侧的多条出线按目标顺序分组，沿侧向做递增偏移（步长 `min(12, 边长度/(n-1))`，最多约 ±24px），并让端口引出段长度随偏移变化，避免主干完全重合；不同侧、不同层的边分别独立路由。
- **正交圆角路由**：连线为 8px 圆角的直角折线，端口先引出 22px stub，再走水平/垂直主干；跨层且左右端口不同高时使用横向 lane，同高直连，路径穿过中间节点时自动选择外侧避让车道，避免从节点内部穿过。选中边加深箭头与线色，端点手柄覆盖在端口锚点上。
- **键盘与作用域**：`Delete` 只在画布获得指针焦点且已选中连线时删除；`Ctrl+C / Ctrl+V` 复制粘贴选中节点，`Ctrl+Z / Ctrl+Shift+Z` 撤销/重做；输入框/文本域/下拉框/可编辑区域内不拦截任何快捷键；`Esc` 优先回滚正在进行的节点拖拽或画布平移，否则取消连线选中。
- **边属性**：`edgeLabels[toNodeId]` 保存连线标签或分支名；`edgeRules[toNodeId]` 保存条件规则，条件类型沿用 `scopeRisk / role / dept / else`。条件规则变更时同步刷新边标签。
- **自动布局**：按拓扑最长路径分层，同层按原 `x` 排序并居中；孤立节点和环上节点放到末尾层；画布宽度随最长层自动扩展。专注画布隐藏左右栏，退出后恢复。
- **草稿与发布**：保存草稿只做结构归一化，不因中间态拦截；发布调用严格校验，显式边不合法时拒绝发布并返回具体节点/分支错误。
- **运行时边界**：`planSteps` 已消费公司自建且已发布的流程拓扑；内置示例模板不参与运行时。旧 `branches` 嵌套图按数组顺序执行，显式 `nextIds` 自由图按条件出线遍历，暂不实现多出线并行汇合；转交/加签、超时与抄送投递、申请单版本锁定仍未接入。结束节点后接抄送当前只表示“审批完成后的旁路通知拓扑”，运行时遍历到 `end` 即停止，暂无抄送投递。

### 4.7 结束节点后抄送、节点复制粘贴与撤销重做

> 2026-11-21 补充需求。先固定行为合同，再按合同实现和验收。

#### 4.7.1 结束节点 → 抄送节点

- 结束节点允许有出线，但出线目标只能是抄送节点；目标为审批、条件、开始、其他结束节点时拒绝，提示“结束节点只能连接到抄送节点”。
- 抄送节点允许没有出线，作为流程末端；抄送节点若继续出线，按普通节点规则校验，仍禁止成环。
- 结束节点仍可被其他节点指向；结束节点本身不产生审批步骤。
- 结束节点四向端口不再禁用；从任一方向拖出都走同一套目标校验。右键结束节点只提供“抄送节点”，新建的抄送节点插入在结束节点之后，而不是插到结束节点之前。
- 合法示例：`开始 → 审批 → 结束 → 抄送`；抄送 `nextIds=[]`。发布校验必须接受该拓扑。
- 当前运行时遍历到 `end` 即停止，因此结束节点后的抄送只作为“审批完成后的旁路通知拓扑”保存和展示；抄送投递仍属于后续运行时能力，不在本次验收范围内。

#### 4.7.2 节点复制 / 粘贴

- 复制对象是当前选中的单个节点，且当前没有选中连线；开始节点、结束节点不可复制。
- 复制的是节点配置快照，不复制入线、出线、连线标签、条件规则和端口侧。
- 粘贴生成一个新节点：新 `id`、标题追加“副本”、`nextIds=[]`、无入线，自动偏移到源节点右下方并夹在当前可见画布内，粘贴后立即选中新节点。
- 粘贴前先把旧链式流程物化为显式边，避免数组顺序产生隐藏边；新节点不继承源节点的 `branches` 子树，条件节点粘贴后分支为空，避免出现悬空子图。
- 重复粘贴生成多个独立副本；复制动作本身不修改流程、不记撤销历史。
- 剪贴板为设计器内存状态，跨模板可粘贴；源模板不存在或源节点已删除时，粘贴落点改为当前可见画布中心。
- `Ctrl+C` 复制、`Ctrl+V` 粘贴；输入框、文本域、下拉框、`contenteditable` 内不拦截，保留系统复制粘贴行为。

#### 4.7.3 撤销 / 重做

- 撤销粒度是“一次用户操作”，按模板保存完整流程快照，而不是逐字段反向补丁。
- 历史覆盖：新建/删除节点、新建/删除/重接连线、拖动节点、自动布局、修改节点配置、修改连线标签/条件、增删条件分支、选择审批人/角色等未保存编辑。
- 每个模板独立保留历史，最多约 60 步；保存草稿或发布成功后，服务端返回新模板对象，历史重置为“已保存状态”，撤销不会跨过保存点。
- `Ctrl+Z` 撤销，`Ctrl+Shift+Z` 重做；另兼容 `Ctrl+Y` 重做。无历史时给出“没有可撤销/重做的操作”，不静默失败。
- 同一输入框连续输入在约 1.2 秒内合并为一步，避免每个字符一步；不同操作即使连续发生也不合并。
- 撤销/重做后恢复当时的选中节点或连线；节点已不存在时回退到流程首节点。
- 撤销/重做本身不再产生新的历史条目；执行后模板标记为草稿，顶部 Toast 显示“已撤销/已重做：操作名”。
- 快捷键作用域限定在画布视口或画布内节点：焦点在画布内，或事件发生在 `[data-wf-viewport]` 内时才处理；工具栏、属性面板和输入控件内不拦截。

#### 4.7.4 验收项

1. 在真实控制台把“结束”节点拖线到“抄送”节点，连线创建成功；拖到审批节点被拒绝并提示“结束节点只能连接到抄送节点”。
2. 保存草稿与发布均接受 `开始 → 审批 → 结束 → 抄送`；手工构造 `结束 → 审批` 的草稿在发布校验时被拒绝。
3. 右键结束节点只出现“抄送节点”，新建后新节点位于结束节点之后。
4. 选中审批节点按 `Ctrl+C`、`Ctrl+V` 后节点数量 +1，新节点标题带“副本”、没有出线且自动选中；按 `Ctrl+Z` 可撤销这次粘贴。
5. 开始、结束节点按 `Ctrl+C` 提示不可复制；焦点在右侧输入框时按 `Ctrl+C/V` 不触发画布复制粘贴。
6. 删除节点、删除连线、拖动节点、修改处理时限后分别按 `Ctrl+Z`，均恢复到操作前；按 `Ctrl+Shift+Z` 恢复操作后状态。
7. 保存草稿后立即按 `Ctrl+Z`，不应撤销到保存前；切换两个模板后各自历史互不影响。


### 4.8 直属上级 / 部门负责人链按节点配置级数

> 补充需求：依次审批选用部门负责人时，可按实际部门架构配置级数；申请人直属上级与部门负责人链合并为同一个来源；申请人本人是部门负责人时不能把自己作为审批人。

#### 4.8.1 行为合同

- 审批人来源合并为“直属上级 / 部门负责人链”，节点字段 `source=dept_chain`；管理端不再新增 `source=manager`，旧模板中的 `manager` 继续兼容，等价于该来源 1 级。
- 节点新增 `maxLevels`（审批级数），范围 1–10，整数；只对该节点的部门负责人链生效，不修改公司默认审批链。旧节点没有 `maxLevels` 时继续回落到默认审批链级数。
- 级数含义：1 级取申请人所在部门的负责人，也就是申请人的直属上级；2 级取上级部门的负责人，依次向上。不是“同一个节点里任选 N 人”，而是按组织层级依次取负责人。
- 申请人本人就是所在部门负责人时，跳过本人，1 级从上级部门负责人开始；上级部门没有负责人时直接跳过该级并继续向上，不生成空步骤。继续跳过重复负责人和没有 `approval:decide` 权限的负责人；链尾是否追加公司管理员由节点 `fallbackAdmin` 开关决定，缺省时沿用默认策略 `includeCompanyAdmin`。
- 兜底开关关闭时，空缺级只跳过、不补公司管理员；如果整条部门负责人链都没有可用审批人，该节点报“没有可用审批人”，申请不能提交，不会静默自动通过。
- 审批方式与级数组合：`依次审批` 将 N 级拆成 N 个串行步骤；`会签` 将 N 级放进同一节点会签；`或签` 只取第 1 级。级数字段在三种方式下都可配置，避免切换方式后丢配置。
- 节点属性面板展示“审批级数”，说明文字收进标签后的 `?` 角标；悬停或键盘聚焦角标时提示“1 级为申请人直属上级；申请人本人是部门负责人时自动从上级部门开始。依次审批按级展开，或签只取第 1 级。”
- “审批人”标签也使用同一套 `?` 角标承载规则说明：“按申请人所在部门逐级向上取负责人；跳过申请人本人、没有负责人的部门层级和无审批权限的负责人”。不再在审批人区域重复显示一行说明文字。
- 审批人来源下方提供“实人预览”：默认以当前控制台账号所属成员为申请人，也可在成员下拉里切换预览申请人；预览直接展示解析后的真实审批人姓名、所属部门或“公司管理员兜底”，不再只显示抽象规则。
- 实人预览必须走真实运行时规则，使用当前未保存的节点快照和公司默认审批策略；级数、审批方式、兜底开关变化后自动重算。预览只读，不创建审批单、不发消息、不标记模板已修改。
- 预览接口为 `POST /api/console/approval-workflows/:id/preview-approvers`，请求体包含节点快照、节点 id 和申请人 id，响应返回 `people[]`（`kind=manager|company_admin`，含从申请人部门向上的 `level`）、`skipped[]`、有效级数、审批方式、兜底状态和是否还有更多审批人。申请人必须属于当前公司。旧节点没有写 `source` 时，预览与运行时一致，按“直属上级 / 部门负责人链”解析，不报来源不支持。
- 预览人员行直接标注“N 级”：部门负责人显示为“N 级负责人 + 姓名 + 部门”，公司管理员兜底显示为“兜底 + 姓名 + 公司管理员兜底”，管理员不需要再根据顺序猜第几级。
- 被跳过的部门层级也会展示，并标明原因：`申请人是本级负责人`、`未设置部门负责人`、`未开通“审批决定”权限`、`负责人账号不可用`。这样配置 3 级时能看到直属部门、上级部门、公司三层，不会因为只显示最后可审批的公司负责人而误以为预览丢数据。
- 审批级数上限不再固定为 10，而是读取当前公司组织树的实际层级数（根公司算 1 级，例如公司 → 部门 → 片区 → 组为 4 级）；输入框 `max`、默认值、已有模板回显都按该上限收敛。超过上限时输入值立即回退到上限，并提示“审批级数不能超过本组织实际层级，最多 N 级”。
- 审批级数变化后立即重算实人预览，不再需要先保存或切换节点。
- 配置级数大于实际可用人数时，预览元信息会标出“配置 N 级，已跳过 M 级”或“配置 N 级，实际只有 M 人可用”，同时保留逐级原因，避免把真实组织链尾当成预览丢数据。
- 没有可用审批人时，预览区直接提示“没有可用审批人；已关闭公司管理员兜底，提交时会被拒绝”，让管理员在保存前发现问题。
- 画布摘要显示“直属上级 / 部门负责人链 · N 级 · 时限”，不再固定显示“最多 10 级”。
- 校验：`maxLevels` 不是 1–10 的整数时，校验与发布拦截并提示“审批节点的审批级数必须是 1–10 的整数”；保存草稿仍沿用现有“允许未完成草稿”的行为。
- 运行时只读取部门 `manager_user_id` 和 `parent_id` 链，不新增组织表字段，也不要求管理员重新维护一套“直属上级”数据。

#### 4.8.2 验收项

1. 新建或编辑审批节点，选择“直属上级 / 部门负责人链”，属性面板出现“审批级数”，默认 3，可输入 1–10。
2. 选择“依次审批”并把级数设为 1，发布后提交申请只生成 1 个审批步骤，审批人是申请人所在部门的负责人。
3. 申请人本人就是所在部门负责人时，同样设 1 级，第 1 步自动落到上级部门负责人，不会出现“审批人不能是申请人”的空链报错。
4. 级数设为 2 时生成 2 个串行步骤：第 1 步为直属上级、第 2 步为上级部门负责人；级数设为 3 时继续向上。上级部门没有负责人时跳过该级，链尾不足且节点兜底开启时才补公司管理员。
5. 级数设为 0、11 或小数时，校验/发布被拒绝；合法 1–10 整数时校验通过。
6. 切换审批方式为会签或或签后，已配置的级数仍保留；或签只取第 1 级，会签按 N 级同节点会签。
7. 旧模板 `source=manager` 打开后显示为“直属上级 / 部门负责人链 · 1 级”，发布与运行时仍按 1 级部门负责人链解析。
8. 上级部门 `d1` 没有负责人、节点兜底关闭时，级数 3 仍会继续读取更高层 `d0` 负责人，只生成 `u3` 一个步骤，不因空级报错；同一场景打开兜底后，链尾补公司管理员 `u4`，生成 `u3 → u4` 两个步骤；整条链都没有负责人且兜底关闭时，提交被拒绝，不会自动通过。
9. “审批级数”下方不再重复显示说明小字；标签后的 `?` 角标悬停、键盘聚焦都能显示完整说明，移开或滚动后消失。
10. 选择“直属上级 / 部门负责人链”后，审批人区域出现实人预览和申请人下拉；默认是当前控制台账号，切换成员后预览按真实组织负责人链刷新。级数从 1 改到 2、打开或关闭兜底后，预览同步变化；整条链为空时显示不可提交提示，而不是空白。
11. “审批人”区域不再单独显示规则说明文字，规则收进“审批人”标签后的 `?` 角标；真实组织已发布模板即使节点没有写 `source`，预览也能正常返回负责人链，不出现“当前审批人来源不支持实人预览”。
12. 实人预览每一行明确显示“N 级负责人”，例如“1 级负责人 张辉权 重庆居易智能科技有限公司”；公司管理员兜底显示“兜底 … 公司管理员兜底”。多级负责人时按 1、2、3… 连续标注。
13. 当前公司组织树最深路径为公司 → 部门 → 片区 → 组时，审批级数输入框最大值为 4、提示“本组织实际最多 4 级”；输入 5 后立刻回退为 4 并提示，预览同步按 4 级重算。
14. 配置 3 级但直属部门负责人无审批权限、上级部门没有负责人时，预览仍列出 1、2、3 级：1 级显示负责人姓名和“未开通‘审批决定’权限，已跳过”，2 级显示部门名和“未设置部门负责人，已跳过”，3 级显示实际可审批的公司负责人；元信息提示“1 人可用；配置 3 级，已跳过 2 级”。


## 五、页面信息架构与布局

### 5.1 管理端「权限审批」

顶部一级页签建议：

1. **流程设计**：模板列表 + 画布 + 属性面板。

## 六、数据模型建议

### 6.1 流程模板与版本表（已落地）

```sql
CREATE TABLE approval_workflows (
  id                   TEXT PRIMARY KEY,
  company_id           TEXT NOT NULL REFERENCES companies(id),
  name                 TEXT NOT NULL,
  description          TEXT NOT NULL DEFAULT '',
  status               TEXT NOT NULL DEFAULT 'draft', -- draft / published / disabled
  scope_mode           TEXT NOT NULL DEFAULT '全部权限点',
  role_mode            TEXT NOT NULL DEFAULT '全部员工角色',
  current_version      INTEGER NOT NULL DEFAULT 0,
  draft_version_id     TEXT,
  published_version_id TEXT,
  created_by           TEXT,
  created_at           INTEGER NOT NULL,
  updated_at           INTEGER NOT NULL,
  deleted_at           INTEGER
);
CREATE UNIQUE INDEX uq_approval_workflow_name
  ON approval_workflows (company_id, name) WHERE deleted_at IS NULL;

CREATE TABLE approval_workflow_versions (
  id              TEXT PRIMARY KEY,
  workflow_id     TEXT NOT NULL REFERENCES approval_workflows(id),
  company_id      TEXT NOT NULL REFERENCES companies(id),
  version         INTEGER NOT NULL,
  status          TEXT NOT NULL DEFAULT 'draft', -- draft / published / superseded
  flow_json       TEXT NOT NULL,
  validation_json TEXT,
  created_by      TEXT,
  created_at      INTEGER NOT NULL,
  updated_at      INTEGER NOT NULL,
  published_at    INTEGER
);
CREATE UNIQUE INDEX uq_approval_workflow_version
  ON approval_workflow_versions (workflow_id, version);
```

`flow_json` 保存节点、分支、审批方式、抄送配置；`validation_json` 保存最近一次校验错误。草稿版本号固定为 `current_version + 1`，重复保存原地更新同一草稿；发布冻结该版本并把旧 published 标为 `superseded`。运行时后续只读已发布版本快照，不直接读草稿。

### 6.2 申请单扩展

`permission_requests` 增加：

## 八、迁移与兼容

1. 历史 `request_type='role'` 和 `request_type='scope'` 的待审批单继续走旧状态机，直到处理完。
2. 新申请单统一写 `request_type='scope'`，并带 `source_role_id`、`workflow_id`、`workflow_version`。
3. 旧 `permission_approval_policies` 不删除；迁移时生成一个“旧策略兼容流程”，只服务历史单。
4. `roles.requestable` 保留字段，但新申请不再读取；`requestable=1` 的旧角色可继续作为历史单的审批依据。
5. `permission_scope_grants` 继续使用，只给申请人个人授权；新单不写 `role_scopes`、不写 `user_roles`。
6. 现有钉钉 A2UI 卡继续复用，卡片正文增加申请角色、个人授权有效期、流程版本，不展示“影响人数”。
7. 历史 `permission_role_grants` 和 `user_roles` 的写入路径只保留给旧角色单，新流程不进入该分支。

## 十、验收标准

1. 任意成员可以申请全部已登记权限点，不再受 `requestable` 角色限制。
2. 成员有多个当前角色时，申请页可选择其中一个；该角色只用于审批策略，不会因审批通过获得新权限。
3. 最后一级通过后，`permission_scope_grants` 写入申请人个人权限和有效期；`role_scopes` 不变，角色下其他成员权限不变。
4. 审批拒绝、超时、申请人离职/禁用时，不写个人授权，申请人能在对话页或钉钉收到“审批未通过”及原因。
5. 同一申请重复审批不重复写授权；授权失败不会显示“已通过”。
6. 流程设计器可新建、保存草稿、校验、发布；条件分支按配置路由；转交、加签、抄送可执行且留审计；发布版本与运行中申请隔离。
7. 页面在 1171×880 下三栏不横向溢出，左/中/右各自滚动，画布节点可选中并与右侧属性联动。
8. 历史待审批单可继续处理，历史授权记录可查。

## 十一、已确认决策

以下三项已由用户确认，作为开发基线：

1. **授权语义**：只给申请人个人授权，不改共享角色，按有效期失效。
2. **多个当前角色**：由申请人选择一个当前角色，作为申请身份与审批策略上下文，不作为授权落点。
3. **流程设计器范围**：完整版，包含顺序审批、条件分支、或签/会签、转交、加签、抄送、超时与通知。

仍建议默认：通知渠道双发（对话页系统通知 + 钉钉机器人私聊），任一失败进入重试，不阻断审批。
