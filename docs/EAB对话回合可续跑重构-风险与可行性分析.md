# EAB 对话回合「可续跑」重构 · 风险与可行性分析

> 目的：回答两个问题——把 `runAgentTurn` 重构成可挂起、可续跑的回合引擎，对项目有什么影响？现在做是否可行？
> 结论先行：**技术上可行，但现阶段整体重构不划算**。建议先做「工具执行托管」（方案 B），再对少数长任务工具做「两段式调用」（方案 C），把挂起重构（方案 A）压到有真实数据支撑时再做。

## 1. 结论

| 问题 | 结论 |
|---|---|
| 能不能做 | 能。数据表（`pending_job_id` / `resume_state_json`）、作业队列、Pub/Sub、跑批 leader 都已就位，缺的是回合引擎本身的可重入化。 |
| 风险大不大 | 大。改动落在对话核心路径，一次改坏 = 网页、钉钉、飞书、定时任务四条入口同时坏。 |
| 现在该不该做 | **不建议**。本地实测数据不支持「慢工具是当前瓶颈」这个前提（见第 5 节）。 |
| 推荐路径 | B（工具执行托管，1 天级）→ C（长任务工具两段式，按工具逐个上）→ A（整体挂起，等数据证明必要） |

## 2. 重构到底要动什么（现状事实）

- `runAgentTurn` 一个函数 **约 600 行**（`routes/chat.ts` 1611–2213 行），回合循环、工具执行、故障转移、澄清、子 Agent、预算统计全在里面。
- 循环内的**闭包状态**（挂起时必须全部序列化，否则续跑不一样）：
  `messages` / `tools` / `allTools` / `allowedToolNames` / `activeToolNames` / `traces` / `stepSeq` / `text` / `reasoning` / `rounds` / `activeModelId` / `failedModelIds` / `clarifyRepairUsed` / `turnId` / `space` / `modelProfile` / `primaryCallPlan` / 预算计数。
- **5 个调用方，语义各不相同**：
  - `routes/chat.ts:3184` 网页流式（SSE 已 `hijack`，断开不中止模型，靠 `abortController` 取消）；
  - `dingtalk-bot.ts:1131` / `feishu-bot.ts:698` 渠道机器人（`bufferModelEvents` 缓冲后一次性下发，还要发卡片）；
  - `schedule.ts:757` 定时任务（无交互，同步等结果）；
  - `routes/chat.ts:1455` 子 Agent（`spawnSubAgents` 里 `await` 每个子 run）。
- **消息落库在回合结束之后**：assistant 消息在 `routes/chat.ts:3353` 才 INSERT。也就是说挂起时「assistant 的 tool_calls + 工具结果」只存在于内存，**必须整段进 `resume_state_json`**，否则续跑拼不出上下文。
- **会话锁**：`acquireAgentSessionLock` 用 `acquireCoordinationLock`（TTL 180s、自动续租）保证同会话回合互斥。挂起时必须**先释放锁**，续跑再抢回来；这段时间里其它回合可以插进来，续跑后的消息顺序需要显式处理。
- **取消**：`cancelAgentRunTree` 只认进程内 `activeRuns` 里的 AbortController。挂起的 run 已经不在运行表里，取消要扩成「取消挂起 run + 取消后台作业 + 通知持有该 run 的实例」（跨实例部分要靠 `realtime-control`）。

## 3. 影响面清单

| 模块 | 影响 | 风险 |
|---|---|---|
| `runAgentTurn` | 拆成「初始化 / 一轮 / 收尾」三段 + 可重入状态 | 高（核心） |
| 消息落库时序 | 挂起前必须落「进行中」占位，续跑改同一条 | 高（会出重复回答/半条消息） |
| 会话锁 | 挂起释放、续跑重抢 | 中 |
| 取消链路 | 从 1 处扩到 3 处（本地/跨实例/作业） | 中 |
| SSE 通道 | 挂起后连接必须结束，续跑要用「事件重放 + 重连」 | 高（前端要改 `chat.js`） |
| 控制台运行树 | 新增 `suspended` 状态与恢复历史 | 低（已做了状态与收尾） |
| 钉钉/飞书 | 卡片消息要支持「先回执、后追加」 | 中 |
| 定时任务 | 无交互，挂起意义小，建议直接不接 | 低 |
| 子 Agent | 子挂起 → 父必须挂起（级联），复杂度接近平方 | 高，建议首版禁用子 Agent 后台化 |
| 清理策略 | 挂起 run 不能按天删 | 低（已排除） |

## 4. 风险登记表

| # | 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|---|
| R1 | 挂起期间别的回合插入同一会话，历史顺序错乱 | 中 | 高 | 挂起前写「占位 assistant 消息」并锁 `session_id + turn_id`，续跑按 turn_id 归并 |
| R2 | 挂起/恢复导致同一条回答重复落库 | 中 | 高 | 用固定 `messageId` + `INSERT OR IGNORE` / 状态列，续跑只更新不新增 |
| R3 | 取消挂起中的 run 取不干净 | 中 | 中 | 取消三方联动（本地 controller / 挂起记录 / 作业），并写下取消原因 |
| R4 | 前端 SSE 断点续传缺失，用户看到半截回答 | 高 | 高 | 先做「按 messageId 重放事件」能力，再开挂起 |
| R5 | 子 Agent 级联挂起把状态机变成树 | 高 | 高 | 首版明确不支持子 Agent 后台化，直接同步执行 |
| R6 | 恢复时模型已被下线/额度用尽 | 中 | 中 | 恢复前重校验模型与额度，失败即 `failSuspendedRun` 并给用户明确说明 |
| R7 | 工具重跑导致重复写入/重复外发 | 中 | 高 | 白名单只放只读工具；写类工具禁止后台化 |
| R8 | 作业在 A 实例执行，恢复在 B 实例（插件实例/权限不在 B） | 中 | 中 | 恢复前校验插件实例可用，否则转同步重试或判失败 |
| R9 | 序列化体积过大（messages 含长工具结果，几十 KB/次） | 中 | 低 | 只存必要轮次；工具结果超长截断并标注 |
| R10 | 回归面覆盖四条入口 | 高 | 高 | 分入口灰度：先只网页、再钉钉、飞书不动、定时任务不接 |
| R11 | 观测盲区：用户只看到「卡住」 | 中 | 中 | 已有 `agent_runs.suspended` + 控制台作业面板，再加一条用户可见的「已转后台」提示 |
| R12 | 改动与其它并行开发冲突（本仓库有多个进程在改同一批文件） | 高 | 中 | 大改前先冻结相关文件，或分文件小步提交 |

## 5. 数据证据（本地实测，2026-11-14）

对活跃库 `.eab-dev/eab.db` 的 `agent_steps` 做耗时分布统计（共 288 步，其中工具步 288 条）：

| 耗时区间 | 步数 | 占比 |
|---|---|---|
| < 1 秒 | 277 | 96.2% |
| 1–3 秒 | 10 | 3.5% |
| 3–8 秒 | 1 | 0.3% |
| 8–30 秒 | 0 | 0% |
| > 30 秒 | 0 | 0% |

- 工具步平均耗时 **135 ms**，最大 **3418 ms**；**没有任何一次超过 8 秒**。
- 结论：在这个库上，「慢工具堵住 SSE」并不存在。生产环境若有跨网插件 RPC、Office 转换、外部系统查询，才可能出现长尾——**需要先在生产侧加度量，而不是先重构**。

## 6. 三个方案对比

| | A 整体挂起重构 | B 工具执行托管（推荐先做） | C 长任务工具两段式（推荐按工具上） |
|---|---|---|---|
| 做法 | 回合循环改状态机，`suspended` + 作业 + 恢复 | 工具仍在回合内同步执行，但执行体进队列：租约、心跳、跨实例排队、可回收 | 工具拆成 `submit_*` 返回 jobId / `get_*_result` 取结果，模型多一轮 |
| 改动面 | `runAgentTurn` 600 行 + 4 条入口 + 前端 | `executeTool`/`executePluginTool` 外包一层队列等待 | 新增工具对 + 提示词引导，不动回合引擎 |
| SSE 是否被释放 | 是 | 否（仍等待，但可观测、可回收、跨实例公平排队） | 是（本轮先结束，下一轮取结果） |
| 实例崩溃后 | 可续跑（复杂） | 作业重跑，run 判 failed 可重试 | 结果在库里，重新提问即可接着取 |
| 主要风险 | R1–R12 全中 | 等待期占用连接、多一次 DB 往返（毫秒级） | 模型要多一轮、工具要成对设计、提示词要引导 |
| 工作量 | 大（多日 + 全量回归） | 小（1 天级，可独立回滚） | 中（按工具逐个上，互不影响） |
| 回滚 | 难（状态机已改） | 容易（开关关掉即回原路径） | 容易（不调新工具即原行为） |

## 7. 如果最终仍要做 A：最小实现顺序与验收门槛

1. **前置**：SSE 事件按 `messageId` 可重放（否则 R4 无解）。
2. **前置**：assistant 占位消息先落库（否则 R1/R2 无解）。
3. 把 `runAgentTurnBody` 抽成 `createTurnState()` + `stepTurn()`，**先做到「同一进程内可逐步驱动」**，不改挂起。
4. 接入 `suspended`：只在网页入口开，只对白名单只读工具。
5. 验收门槛（缺一不合并）：
   - 未开开关时，四条入口行为与升级前逐字一致；
   - 开关下连续 200 次回合无重复回答、无半条消息、无孤儿 `suspended`；
   - 杀进程重启后，挂起 run 要么续跑成功、要么明确 failed；
   - 取消链路在「挂起中 / 作业执行中 / 恢复中」三个时刻都能停。

## 8. 度量已落地（决定要不要做 A 的依据）

已实现，不再只是建议：

- **看板**：控制台 → 系统 → 并发与队列 → 「工具耗时（近 7 天）」，逐工具给出 调用数 / p50 / p95 / 最长 / 超阈值次数，顶部 pill 显示「慢工具 N 次」或「无慢工具」。
- **接口**：`GET /api/console/tool-metrics?days=7&limit=10`（控制台鉴权）；阈值默认 8 秒，可用 `EAB_TOOL_SLOW_MS` 覆盖。
- **日志**：任一步工具耗时超过阈值时写 `[eab] 慢工具：<tool> 耗时 <ms>ms（run <id>）`，与看板读同一份 `agent_steps.duration_ms`，纯只读聚合、不改写库路径。
- **实时在途**：同一页新增「正在执行（实时）」表，显示此刻占用名额、尚未返回的工具与已耗时（进程内登记，随名额释放自动注销；`/api/console/concurrency` 返回 `inflight` / `inflightTotal`）。卡住的回合不用等跑完就能看见。
- **现状快照**（2026-11-14 实测，近 7 天 238 次调用）：p95 最高为 `plugin:dsh-cy-api:*` 约 1.06 s，其余工具 p95 均在 300 ms 以内，**慢工具 0 次**。

判定规则不变：出现「p95 > 5s 且集中在少数工具」→ 做 C；出现「大量回合总耗时 > 60s」→ 才值得做 A。

## 9. 一句话回答

可行，但不是现在该做的事。**先把慢的地方量出来、把工具执行搬进队列（B）、把少数长任务工具做成两段式（C）**，这三步都是低风险、可回滚、当天能上的；整体挂起重构留到数据证明它必要时再做，否则就是拿对话主链路去赌一个还没被证实的问题。
